    1 Introduction¶

    1.1 Scope¶

    This part specifies the DPM-XL Script Document: a JSON serialisation of the complete set of DPM-XL Operations applicable to one module version, together with the metadata required to evaluate them.

    A Script Document is the deliverable that a DPM authority may publish and that a validation engine is expected to be able to consume. It is generated from the DPM-ML metamodel (see Information Model §5 DPM-ML) and is intended to be the only input an engine needs, besides the reported data itself.

    This part is normative. It occupies the same position as the Grammar: where the grammar defines what a well-formed DPM-XL expression looks like, this part defines what an engine actually receives and how it must be interpreted.

    What this part specifies is an encoding, and only an encoding. Three things are therefore outside its scope, and are named here because each has at some point been mistaken for its business:

    • What an expression means. The semantics of every Operator belong to the Operators part and the Information Model. This part encodes Operations whose meaning is settled elsewhere; where it appears to constrain meaning, it is citing those parts, not adding to them.
    • Whether an expression is meaningful. Type agreement between operands, the admissibility of an argument to an Operator, and every other question of semantic analysis are settled before a Script Document is produced. A Script Document is the output of a pipeline whose semantic analysis has already passed, so this part neither restates those rules nor asks a Consumer to re-derive them.
    • What a Consumer produces. The result of evaluating a document — its outcome categories, counts, messages and report structure — is implementation-specific by design. What is standardised here is the input an engine receives, so that independent engines consume the same documents; what they emit is their own concern.

    The structural validation rules of §5.3 mark the boundary precisely: each is decidable from the document alone, without knowing what any Operator means, without a DPM database, and without an instance.

    1.2 Why a Serialised Script Format¶

    A DPM-XL expression is not self-contained. The expression

    with {tC_28.00, default: 0, interval: true}: {c040} >= {c050}

    denotes nothing until C_28.00 is resolved to a table version, c040 and c050 to sets of Variables, and the enclosing with context to a fallback value and an interval-arithmetics setting. All of that lives in the DPM. Publishing expression strings alone would therefore oblige every engine to embed a copy of the DPM database and reimplement its resolution logic.

    The Script Document exists to remove that obligation. Five properties motivate it:

    1. Self-containment. Every Operand carries its own fully resolved coordinates and Variable identifiers, including data types. Evaluation requires no lookup outside the document.
    2. Decoupling. Engines should be able to run the validations without needing to access the DPM database.
    3. Determinism. Range expansion, with propagation and Operand index assignment are performed once, by the authority. Two conforming engines therefore combine exactly the same Variables in exactly the same pairs.
    4. Auditability. Because the expansion is published rather than recomputed, a validation result can be traced to a specific Variable set, and two releases of the same module can be diffed mechanically.
    5. Deployment. One file per module version, transferable and cacheable, with no database dependency.

    1.3 Relationship to the Other Parts of This Specification¶

    Part Governs
    Information Model The data structures DPM-XL operates on: Recordsets, Records, Components, Variables, null treatment.
    Operators The semantics of each Operator — signature, output type, behaviour. Authoritative for meaning.
    Grammar The concrete surface syntax of DPM-XL expressions.
    Script Format (this part) The serialised, resolved form in which Operations are published and consumed. Authoritative for encoding.

    This part defines no semantics of its own. For every Operator it specifies the encoding and refers to the Operators part for behaviour. Where an encoding rule here appears to imply a semantics that the Operators part contradicts, the Operators part prevails.

    1.4 Conformance¶

    The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY and OPTIONAL are to be interpreted as described in RFC 2119.

    Two conformance targets are defined:

    • A conforming Producer is a process that emits Script Documents. It MUST satisfy every requirement in §5.1 and MUST emit only documents that satisfy the structural validation rules of §5.3.
    • A conforming Consumer is a process that reads Script Documents and evaluates the Operations they contain. It MUST satisfy every requirement in §5.2.

    A Script Document is valid if and only if it satisfies every rule in §5.3.

    Encoding, media type and file naming are specified in §3.1.

    1.5 Terminology¶

    Term Definition
    Script Document A single JSON document conforming to this part.
    Module Object The value of the single member of the root object; carries all content for one module version (§3.2).
    Operation Object The serialised form of one OperationVersion for this module version (§3.10).
    Node One JSON object in an abstract syntax tree, discriminated by class_name (§4.1).
    Operand Node A Node denoting data, a literal or a named value rather than an Operator: VarID, Constant, Scalar, Set, Dimension, ParameterRef, PreconditionItem.
    Operator Node Any Node that is not an Operand Node. This covers the Operator classes proper, the parenthesised expression ParExpr (§4.10), and the two clause classes GroupingClause and AnalyticClause (§4.19, §4.20). The "Kind" column of §4.1.2 names these three groups separately, for orientation; wherever this part says Operator Node it means the whole complement of Operand Node.
    Datapoint Reference One entry of a VarID.data array: a Variable identifier, the resolved coordinates of the cell holding it, and a Position Index component on each axis that varies within the Operand (§4.3).
    Position Index The (x, y, z) triple locating a Datapoint Reference on the row, column and sheet axes of its Operand. A component is present only on an axis that varies within the Operand (§2.4).
    Module Parameter A named execution-time value — a Scalar or a Scalar Set — declared in parameters (§3.9) and read by a ParameterRef Node (§4.8), which carries its fallback.
    Resolved Said of an Operand that carries its own complete coordinates, fallback value and interval setting, independent of any enclosing lexical context (§2.3).

    Throughout this part, "Variable" means a DPM Variable as defined in the Information Model, identified by its VariableID. JSON member names are written in code style; DPM-ML table and column names are written in italics.

    A cross-reference of the form §X.Y always denotes a section of this part. References to other parts always name the part, as in "Operators §7" or "Information Model §5.3".
