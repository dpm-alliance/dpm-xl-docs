    2 Structure and Concepts¶

    This chapter explains the shape of a Script Document and the five concepts needed to read one. It is expository; the normative field-by-field rules are in §3 and §4.

    2.1 The Document at a Glance¶

    A Script Document is a JSON object with exactly one member. Its name is the taxonomy module URI; its value is the Module Object.

    {
  "http://www.eba.europa.eu/eu/fr/xbrl/crr/fws/corep/4.2/mod/corep_le": {

    "format_version": "1.0",            // ── identification
    "module_code": "COREP_LE",
    "module_version": "3.3.0",
    "framework_code": "COREP",
    "dpm_release":  { "release": "4.3", "publication_date": "2026-06-28" },
    "dates":        { "from": "2026-03-31", "to": null },

    "operations":   { "EGDQ_0053": { … } },  // ── the rules
    "preconditions":{ "p_395095":  { … } },

    "variables":              { "5488018": "m" },  // ── dictionaries
    "precondition_variables": { "395095": "b" },
    "tables":       { "C_28.00": { "variables": {…}, "open_keys": {…} } },
    "parameters":   { "WAIVCONS_C10": "String" },

    "dependency_information": { … },        // ── execution planning
    "dependency_modules":     { … }
  }
}

    The fourteen members of the Module Object fall into four groups:

    Group Members Purpose
    Identification format_version, module_code, module_version, framework_code, dpm_release, dates What this document is, which revision of this specification it was written to, and when it applies.
    Rules operations, preconditions The Operations, as resolved abstract syntax trees.
    Dictionaries variables, precondition_variables, tables, parameters Type and structure information for everything the rules reference, and the Module Parameters they read.
    Execution planning dependency_information, dependency_modules Which rules can run on a single instance, and what the others need.

    2.2 Keying by Module URI¶

    The document is keyed by the XBRL taxonomy module URI rather than by module code. This makes a Script Document addressable directly from a reported instance: an engine that has opened an instance knows its entry-point URI and can select the applicable document without consulting a code mapping. The redundant module_code and module_version members are retained for human use and for cross-checking.

    The same URI serves as the key in dependency_modules, so cross-module references are expressed in exactly one namespace.

    2.3 Concept 1 — Resolved Operands¶

    In DPM-XL surface syntax a with clause factors out coordinates shared by several Operands:

    with {tC_28.00, default: 0, interval: true}: {c040} >= {c050}

    In a Script Document no such context exists. The with clause is pushed down into every leaf, and each VarID Node independently carries its table, its coordinates, its fallback value and its interval-arithmetics setting:

    { "class_name": "BinOp", "op": ">=",
  "left":  { "class_name": "VarID", "table": "C_28.00", "column": "040",
             "default": 0, "interval": true, "data": [ … ] },
  "right": { "class_name": "VarID", "table": "C_28.00", "column": "050",
             "default": 0, "interval": true, "data": [ … ] } }

    The consequence is that the abstract syntax tree has no scoping rules. A Node can be evaluated, cached, relocated or reported on in isolation, and a Consumer needs no environment or symbol table.

    2.4 Concept 2 — Range Expansion and Position Indices¶

    Surface DPM-XL selects ranges: {c070-190}, {r*}, {(r0010, r0015)}. A Script Document contains no ranges. Every selection is expanded into an explicit list of Datapoint References in VarID.data.

    Each entry of that list carries two different kinds of information, and keeping them apart is the whole of this concept:

    • Where the cell is — its row, column and sheet codes. Every entry carries these, on every axis the table version has, whatever the selection happened to fix. They identify the cell.
    • Where the cell sits in the Operand — its Position Index, the components x, y and z. These appear only on an axis that varies within the Operand. They are what aligns one Operand against another.

    The VarID itself carries a third thing: the coordinate the selection pinned, if any. {tTab1, r100, c*} pins the row, so the VarID carries row: "100". Whether each entry then repeats row: "100" is a Producer's choice — both conventions are in circulation (§4.3.2) — so a Consumer reads a cell's position from its entry and falls back to the VarID for an axis the entry omits.

    Consider a table Tab1 with rows 100/200/300, columns 100/200 and sheets A/B, whose cells hold the Variables shown:

    Sheet A

    Column 100 Column 200
    Row 100 1 4
    Row 200 2 5
    Row 300 3 6

    Sheet B

    Column 100 Column 200
    Row 100 7 10
    Row 200 8 11
    Row 300 9 12

    The Operand {tTab1, r100, c*, s*} fixes the row and varies the column and sheet axes. It expands to a VarID carrying row: "100" once, and four entries indexed on y and z:

    { "class_name": "VarID", "table": "Tab1", "row": "100",
  "interval": true, "default": 0,
  "data": [
    { "y": 1, "z": 1, "row": "100", "column": "100", "sheet": "A", "datapoint": 1,  "operand_reference_id": … },
    { "y": 2, "z": 1, "row": "100", "column": "200", "sheet": "A", "datapoint": 4,  "operand_reference_id": … },
    { "y": 1, "z": 2, "row": "100", "column": "100", "sheet": "B", "datapoint": 7,  "operand_reference_id": … },
    { "y": 2, "z": 2, "row": "100", "column": "200", "sheet": "B", "datapoint": 10, "operand_reference_id": … }
  ] }

    x is absent from the entries because the row axis does not vary; row is present on them all the same.

    Axis assignment

    x indexes rows, y indexes columns, z indexes sheets. This is normative and matches the DPM-ML OperandReference table.

    A wildcard that resolves to a single code produces a fourth case, and it is the one that catches implementations out: nothing is pinned onto the VarID, and no index is emitted either, because the axis does not vary. §4.3.2 specifies all four states; the practical rule is that a Consumer MUST read an entry's position from the entry, never from the VarID.

    Positional matching¶

    Position Indices are what make a resolved tree evaluable. When an Operator combines two Operands that each expand to several Datapoint References, it combines the entries that share the same Position Index, and produces one result per index. The index is therefore the format's substitute for the Key Components that would align Records in the Information Model.

    Given {tTab1, r100, c*, s*} = 2 * ({tTab1, r200, c*, s*} + {tTab1, r300, c*, s*}), the index (y=1, z=1) selects Variable 1 on the left and Variables 2 and 3 on the right, yielding 1 = 2 * (2 + 3); index (y=2, z=2) yields 10 = 2 * (11 + 12); and so on for four results in total.

    Alignment is on the axes the two Operands share, not on the arity of their index sets. An Operand that varies over sheets alone combines quite happily with one that varies over columns and sheets: it joins on the sheet and broadcasts along the column, giving one result per column-and-sheet. An Operand with no varying axis at all — a single cell — broadcasts across everything. §4.1.5 gives the rule.

    2.5 Concept 3 — Preconditions Are Operations¶

    A precondition is an Operation like any other. DPM-ML classifies Operations by type (Information Model §5.1), and a Precondition is the type whose job is to decide whether one or more validations apply. Its only constraint is on the output: where a Validation may yield a Scalar Boolean or a Recordset of Booleans, a Precondition may yield only a Scalar Boolean — one verdict per instance, because a rule is either applied or not.

    Everything else about it is unrestricted. Any DPM-XL expression may be a precondition provided it reduces to a scalar Boolean: it may select facts, aggregate them, compare them, apply clauses, read a Module Parameter. A precondition tree is subject to §4 in full, exactly as an Operation tree is.

    preconditions is nonetheless a separate section, for two reasons that have nothing to do with the language:

    • The linkage is inverted relative to DPM-ML. Instead of each Operation naming its precondition, each precondition lists the Operations it gates in affected_operations. One precondition therefore serves many Operations without duplication, and a Consumer evaluates each precondition once per instance rather than once per gated rule.
    • A false precondition means skipped, not failed. The two sections drive different reporting outcomes, so keeping them apart keeps the outcome unambiguous.

    Filing indicators do get their own dictionary, precondition_variables, and that separation is structural: DPM-ML types every Variable as fact, filingindicator or key, and a filing indicator is not a fact. The dictionaries are therefore disjoint by construction (§3.8). A precondition that selects facts types them in variables like anything else.

    2.6 Concept 4 — Scope Attributes¶

    In DPM-ML an OperationVersion applies in many scopes, each with its own IsActive, Severity and FromSubmissionDate (see Information Model §5.3 Operation Scope). A Script Document covers exactly one module version, so the scope for that module version is resolved and flattened onto the Operation Object as severity and from_submission_date. Inactive scopes are omitted entirely: presence in a Script Document is the assertion that the Operation is active.

    The same Operation may therefore appear with severity: "error" in one module's document and severity: "warning" in another's. Severity is a property of the scope, never of the rule. Three values occur — error, warning and info — and all three are reportable outcomes (§3.10).

    One case the flattening cannot express is an Operation whose severity depends on which of several mutually exclusive dependencies the reporter filed, because there the document's own module version appears in more than one active scope. §5.7.2 records the limitation.

    2.7 Concept 5 — Instance Dependencies¶

    dependency_information partitions the Operations into those evaluable from the instance at hand and those that are not:

    • intra_instance_validations — evaluable against a single reported instance of this module version.
    • cross_instance_dependencies — each entry names the module versions required, the Operations affected, and the reference-date window over which the dependency holds.

    The two groups cover every Operation and never overlap (§5.3, rule V-14). An Operation missing from both is the failure mode §5.7.1 records, and leaves the rule unevaluable.

    Two subtleties matter. Within one entry the required modules are conjunctive. They are alternatives only where alternative_dependencies declares their modules mutually exclusive, never by inference (§3.11.2). And an entry MAY name the document's own module at a different reference period — a self-dependency, which is how time_shift is declared, forwards as well as backwards (§3.11.3).

    dependency_modules then supplies the table structures of those foreign modules, so that cross-module Operands remain resolvable without loading the foreign Script Document.

    It is worth noting that dependencies work somehow similarly to preconditions, in the sense that if an instance for a dependency module is not provided, the validations with that dependency are skipped.

    2.8 What Is Deliberately Absent¶

    A Script Document is not a substitute for the DPM. It omits, by design:

    • Labels and descriptions. No natural-language names for Variables, tables or rules. Reporting messages are the consumer's concern.
    • Dimensional composition. A datapoint is an opaque Variable identifier; the Property/Category/Context composition behind it is not serialised.
    • Rendering. Row, column and sheet codes are present as coordinates; header structure, ordering and presentation are not.
    • Item enumerations. Scalar Nodes carry item QNames; the SubCategories they belong to are not serialised.
    • Parameter bindings. parameters (§3.9) declares which Module Parameters exist and what type each has, and each ParameterRef carries the fallback for its own reference (§4.8.1). What the document cannot carry is the binding: the value itself comes from the execution environment, and an unbound Parameter falls back to its default or to null.

    An engine that must produce dimension-aware error messages, or resolve a QName to its enumeration, still needs the taxonomy or the DPM. §5.5 records the extension points reserved for enlarging this boundary.
