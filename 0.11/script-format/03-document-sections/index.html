    3 Document Sections¶

    This chapter specifies each section of a Script Document normatively. Abstract syntax trees are specified separately in §4.

    Throughout, "member" means a JSON object member. Unless a member is marked OPTIONAL, it MUST be present. A member marked nullable MAY have the JSON value null; a member marked OPTIONAL MUST be omitted rather than set to null when it carries no value, except where stated otherwise.

    3.1 Serialisation and Root Object¶

    A Script Document MUST be a JSON document as defined by RFC 8259, encoded in UTF-8 without a byte-order mark.

    The root MUST be a JSON object with exactly one member. The member name MUST be the absolute URI of the XBRL taxonomy module entry point. The member value is the Module Object (§3.2).

    Producers SHOULD name files <module_code>-<module_version>.json and MAY serve them with media type application/json.

    Producers MAY emit whitespace-formatted JSON for legibility. Consumers MUST NOT depend on formatting, member order or key order anywhere in the document.

    Every object this part specifies is closed. Where a section gives the members of an object, those are the only members that object may carry: a Producer MUST NOT add any other, and a Consumer MUST reject a document that does (§5.2, requirement 2). This holds uniformly, whether or not a rule of §5.3 restates it for a particular object — several do, because those objects are where the failure was seen in practice, not because the others are open.

    Size

    A document for a large module runs to several megabytes, dominated by expanded data arrays and by the variables dictionary. Producers SHOULD offer compressed transfer; the format compresses well, since both are highly repetitive.

    3.2 Module Object¶

    Member Type Notes
    format_version String Version of this specification the document was generated against. §3.2.1.
    module_code String DPM code of the module. MUST equal ModuleVersion.Code.
    module_version String MUST equal ModuleVersion.VersionNumber.
    framework_code String DPM code of the owning framework.
    dpm_release Object §3.3
    dates Object §3.4
    variables Object §3.5
    tables Object §3.6
    preconditions Object §3.7
    precondition_variables Object §3.8
    parameters Object §3.9
    operations Object §3.10
    dependency_information Object §3.11
    dependency_modules Object §3.12

    All fourteen members are REQUIRED. operations, preconditions, tables, precondition_variables, parameters, dependency_modules and the arrays within dependency_information MAY be empty. variables MAY be empty too, but only where tables is empty as well — it is not chosen independently, but derived as the union of tables[*].variables (§3.5, rule V-8).

    Consumers MUST reject a document containing an unrecognised member of the Module Object. Members are added only by a revision of this specification (§5.6).

    3.2.1 format_version¶

    format_version names the version of this specification that the document was generated against — not the DPM release, which dpm_release carries (§3.3), and not the module, which module_version carries.

    It MUST be the MAJOR.MINOR version of this specification, as published: "1.0" for this version. A Producer MUST emit the version it actually generated against, and MUST NOT emit a version it does not implement in full.

    "format_version": "1.0"

    A Consumer MUST reject a document whose format_version names a MAJOR version it does not implement, and MAY reject one naming a higher MINOR version of a MAJOR version it does implement. It MUST NOT reject a document naming a lower MINOR version, since MINOR revisions are non-breaking (§5.6).

    The member exists because the alternative was tried and failed. Without it, a document written to one revision and a malformed document are indistinguishable: a Consumer can report only an unrecognised or missing member, and cannot say which revision it was handed. §5.6 records the two documents in circulation that demonstrate this.

    3.3 dpm_release¶

    Provenance of the DPM content from which the document was generated.

    Member Type Notes
    release String DPM release code, e.g. "4.3". MUST equal Release.Code.
    publication_date String ISO 8601 calendar date, YYYY-MM-DD. Date the Script Document content was published.

    publication_date is the publication date of this generated artefact, which MAY be later than the publication date of the DPM release itself. It is provenance only and MUST NOT affect evaluation.

    Documents of the same framework are not necessarily generated from the same release. A module version need be regenerated only when the module version itself changes, so a set of documents held together may name several releases. Consumers MUST therefore treat dpm_release as a property of the individual document and MUST NOT assume that two documents they hold agree on it.

    3.4 dates¶

    The reference-period window of the module version: the reference periods the module version covers, which are the periods being reported about, not the dates on which data is submitted.

    Member Type Notes
    from String ISO 8601 date. First reference date covered. MUST equal ModuleVersion.FromReferenceDate.
    to String, nullable Last reference date covered, inclusive. null means the version is open-ended.

    If to is non-null it MUST be greater than or equal to from.

    Consumers MUST NOT evaluate a Script Document against an instance whose reference date falls outside [from, to].

    null here, "" in dependency_information

    An open-ended window is spelled null in dates.to but as the empty string in cross_instance_dependencies[*].to_reference_date (§3.11). The two members mean the same thing and are encoded differently. Consumers MUST accept both spellings in the member where each occurs, and MUST treat the empty string as "no upper bound" rather than as a malformed date.

    3.5 variables¶

    The Data Type dictionary of the fact Variables of this module, consolidating the per-table dictionaries of §3.6.

    • Member name: the VariableID, as the decimal representation of a positive integer in a JSON string.
    • Member value: a Data Type code (below), as a String.
    "variables": { "85015": "m", "85083": "b", "85141": "p" }
    Code Data Type Code Data Type
    i Integer m Monetary
    r Decimal p Percentage
    s String (non-empty) d Date
    es String (including empty) dt Date-time
    b Boolean u URI
    t True o Ordinals
    e Enumeration

    Codes MUST be drawn from this set, which is DataType.Code in DPM-ML. A Consumer MUST accept all thirteen; a document is not obliged to use any particular one.

    variables MUST be exactly the union of the variables dictionaries of every entry of tables (§5.3, rule V-8). It is therefore keyed by table membership, not by use: it covers every Variable of every referenced table, including — typically in the large majority — Variables that no Operation in the document references.

    It is the Consumer's authority for the Data Type of an Operand, which governs interval arithmetics, null treatment and the admissibility of each Operator. Every datapoint of a VarID whose table is a member name of tables MUST appear here (§5.3, rule V-9); datapoints of Operands selecting from foreign modules are typed in dependency_modules instead (§3.12).

    The Data Type is a function of the VariableID alone. A Variable MAY occur in several tables, and where it does, every dictionary that mentions it MUST assign it the same Data Type (§5.3, rule V-26).

    This invariant is what makes type integrity enforceable on the loading path. Under the EBA XBRL-CSV architecture a fact is reported as a Variable ID, its value, and any open-key values; there is no coordinate in the instance to key on. A Consumer therefore validates the type of an incoming fact with a single lookup on the VariableID, before knowing which table or Operation will consume it, and MAY treat variables as one flat dictionary rather than resolving per table.

    3.6 tables¶

    Structure of every table version referenced by any VarID in operations.

    • Member name: the table version code, e.g. "C_28.00".
    • Member value: an object with the members below.
    Member Type Notes
    variables Object The Variables of this table, in the Data Type dictionary form of §3.5.
    open_keys Object Open Key dictionary: Key Component code → Data Type code. MAY be empty. 
    "C_29.00": {
  "variables": { "85015": "m", "85014": "m", "85083": "b" },
  "open_keys": { "GCC": "s", "INC": "s" }
}

    variables serves two purposes, and the second is the one that cannot be obtained elsewhere:

    1. it repeats the Data Type of each Variable, which §3.5 also carries; and
    2. it declares table membership — which Variables belong to this table.

    Membership is recorded nowhere else in the document. Under the EBA XBRL-CSV architecture a reported instance is split into one file per table, so a Consumer uses this member to determine which Variables to load from each file. It MUST NOT attempt to derive membership by collecting the table and datapoint values of the VarID Nodes in operations. A table contains every Variable of its rendering, and only a fraction of those is typically referenced by any Operation; membership derived from the rules would omit the rest, and the Consumer would then fail to load data it is required to validate against.

    A Variable MAY belong to more than one table (§3.5). Its Data Type is the same in every table that lists it.

    open_keys declares the Key Components that are open in this table — those whose values are not fixed by the rendering but supplied by the reporter, producing a variable number of Records. They are the Key Components available to a GroupingClause (§4.19), to a GetClauseOp (§4.23) and to the condition of a WhereClauseOp (§4.21) or SubClauseOp (§4.22). Their values are Data Type codes drawn from the same set as §3.5; e, s, i and d occur.

    Codes are version-scoped

    Open Key and Dimension codes are properties of the module version, not stable identifiers. The DPM remodelling introduced in release 4.2 renamed many of them with a q prefix: COREP_LE 3.1.0 groups by GCC, INC while 3.3.0 groups by qGCC, qINC. Consumers MUST resolve these codes against the open_keys of the document in hand and MUST NOT carry them across documents.

    3.7 preconditions¶

    The preconditions gating the Operations of this document. See §2.5.

    • Member name: the precondition code. No format is imposed on it. A Producer MAY derive it from the tree — "p_395095", "p_395096_395097_395098", prefixing the variable_ids of a filing-indicator precondition, is one such convention — but a Consumer MUST treat the code as opaque and MUST NOT parse anything out of it.
    • Member value:
    Member Type Notes
    code String MUST equal the member name.
    version_id Integer Identifier of this precondition version within the content the Producer generated it from. See the note at §3.10.
    ast Object Root Node of the precondition tree.
    affected_operations Array of String Codes of the Operations this precondition gates. MUST be non-empty.

    The following is COREP_LE 3.1.0's p_395096_395097_395098 verbatim:

    "p_395096_395097_395098": {
  "code": "p_395096_395097_395098",
  "version_id": 395096,
  "ast": { "class_name": "BinOp", "op": "and",
           "left":  { "class_name": "BinOp", "op": "and",
                      "left":  { "class_name": "PreconditionItem",
                                 "variable_id": 395096, "variable_code": "C_27.00" },
                      "right": { "class_name": "PreconditionItem",
                                 "variable_id": 395097, "variable_code": "C_28.00" } },
           "right": { "class_name": "PreconditionItem",
                      "variable_id": 395098, "variable_code": "C_29.00" } },
  "affected_operations": [ "EGDQ_0056", "EGDQ_0057" ]
}

    3.7.1 What a precondition tree may contain¶

    A precondition ast is an Operation tree and is governed by §4 in full. Any Node class permitted in an Operation is permitted here, and no Node class is reserved to preconditions or excluded from them. The encoding of a precondition is the encoding of an Operation; there is no second grammar of Nodes for this position.

    What a precondition may mean is settled elsewhere: a Precondition is an Operation type that yields a Scalar Boolean — exactly one Boolean value per instance under validation — against a Validation's "Scalar Boolean value or a Recordset with Scalar values" (Information Model §5.1). That is a semantic constraint on the expression, not on its serialisation, and it holds of the surface syntax exactly as it holds here.

    One consequence of it is structural, and is checked: the tree MUST vary on no axis, so axes(idx(ast)) MUST be empty in the notation of §4.1.5 (§5.3, rule V-12). A tree that varies on an axis yields a Recordset of Booleans, and there would be no single verdict on which to gate. It is the axes that decide this, not the cardinality of the index set: a single-cell selection has one index whose components are all absent, so it is a Scalar and a perfectly good precondition operand — {tC_26.00, r030, c010} > 0 is well formed — while a selection over a range is not, however few cells the range holds.

    A precondition MAY therefore select facts, aggregate them, filter them and compare the result — sum({tC_29.00, c050}) > 0 is a well-formed precondition. Where it does, its VarID Nodes are resolved and typed exactly as in an Operation: their table MUST be declared in tables or dependency_modules[*].tables, and their datapoints MUST be typed in variables (§5.3, rules V-9 and V-10, which apply to preconditions as much as to operations).

    In practice, preconditions are simpler than the format allows

    Almost every precondition in circulation is a bare PreconditionItem or a conjunction of them, and an implementation built only for that shape will appear to work for as long as no author needs anything more. Since the encoding admits any Operation tree, an implementation that dispatches on class_name generically — as it already must for operations — gets the general case for free and will not be surprised later.

    3.7.2 Linkage and evaluation¶

    Every code in affected_operations MUST be a member name of operations. An Operation MAY be gated by more than one precondition; where it is, all of them MUST hold.

    Consumers MUST evaluate a precondition before any Operation it gates, and MUST skip — not fail — every gated Operation when it evaluates to false. A precondition evaluating to null MUST be treated as false, so the gated Operations are skipped rather than failed.

    A precondition is evaluated once per instance, not once per gated Operation: the inverted linkage exists precisely so that a Consumer need not re-evaluate it for each rule (§2.5).

    3.8 precondition_variables¶

    Data Type dictionary for the filing-indicator Variables referenced by PreconditionItem Nodes (§4.9), in the form of §3.5.

    "precondition_variables": { "395095": "b", "395096": "b", "395097": "b" }

    Values MUST be "b" (Boolean). Identifiers in this dictionary are drawn from a space disjoint from variables (§5.3, rule V-11) and MUST NOT be interpreted as fact Variables.

    The disjointness is structural, not a convention of this format: DPM-ML assigns every Variable a type — fact, filingindicator or key — and a filing indicator is a distinct kind of object from a reported fact, with its own identifier. It is this that earns filing indicators a dictionary of their own; it is not a consequence of preconditions being restricted to them, which they are not (§3.7.1).

    This dictionary therefore does not cover a precondition's other Variables. A precondition that selects facts types those in variables (§3.5), alongside every other fact Variable in the document.

    3.9 parameters¶

    The Module Parameters of this module version: named values supplied to the engine at execution time rather than reported in the instance, read by ParameterRef Nodes (§4.8). They are the serialised counterpart of the Parameter Selection, Information Model §3.1, which is authoritative for their semantics.

    • Member name: the Parameter code, e.g. "BM".
    • Member value: the declared Data Type, as a String, from the vocabulary below.
    "parameters": {
  "BM": "String",
  "FINANCIAL_YEAR_END_MONTH": "Integer",
  "SUBJECT_CONSOLIDATED": "Boolean"
}

    3.9.1 Declared Data Types¶

    Information Model §3.1.1 defines twelve Parameter types, six Scalar and six Set. This part spells each as the surface type word with its initial letter capitalised, and Set followed by the capitalised scalar type name:

    Surface syntax param_type Surface syntax param_type
    number "Number" set-number "SetNumber"
    integer "Integer" set-integer "SetInteger"
    string "String" set-string "SetString"
    date "Date" set-date "SetDate"
    boolean "Boolean" set-boolean "SetBoolean"
    item "Item" set-item "SetItem"

    The mapping is mechanical, so a Producer and a Consumer arrive at the same spelling independently. It is also the convention Constant.type_ follows (§4.4), which keeps one vocabulary across the format.

    A Set-typed Parameter takes a set of values of the corresponding Scalar type and is usable where a Scalar Set is expected — as the right-hand side of in (§4.12), for instance — but not where a Scalar is. §4.8.1 gives the default encoding for all twelve.

    3.9.2 Values, defaults and unbound Parameters¶

    parameters declares that a Parameter exists and what type it has. It carries no value: a binding is supplied by the execution environment alongside the data instances, and how it is delivered is outside the scope of this part (Information Model §3.1.4).

    A default is carried per reference, on the ParameterRef Node (§4.8), not on this declaration — the surface syntax likewise attaches it to the selection, {p_threshold, number, default: 0}. Resolution is therefore three-stepped, and a Consumer MUST apply it in this order (Information Model §3.1.2):

    1. the value bound by the execution environment for that Parameter, if one was supplied;
    2. otherwise the default of the ParameterRef being evaluated, if it is non-null;
    3. otherwise null.

    Step 3 is not an error. An unbound Parameter with no default evaluates to null, and the Operation proceeds under the null treatment of Information Model §4 like any other null. A Consumer MUST NOT set the Operation aside on that ground, and MUST NOT refuse to load a document because a Parameter is unbound.

    Because the default belongs to the reference, two ParameterRef Nodes reading the same Parameter MAY declare different defaults, and a Consumer MUST honour each where its own reference is evaluated. Producers SHOULD nonetheless keep them consistent within a document, since a Parameter that falls back to different values in different rules is difficult to reason about.

    Every ParameterRef.code in the document MUST be a member name here, and its param_type MUST equal the type declared here (§5.3, rule V-29). A Producer SHOULD NOT declare a Parameter that no ParameterRef reads.

    3.9.3 What a Parameter is for¶

    A Parameter is a property of the reporting entity, of the submission, or of the supervisory regime — not of the reported data. It lets one Operation serve executions that differ only in a threshold, a date, a permitted set of codes or a configuration flag. Three kinds arise in practice:

    • Facts about the institution — its business model, the month its financial year ends, whether it reports on a consolidated basis, its systemic designation.
    • Supervisory permissions and waivers — which approach to operational risk the institution is authorised to use, whether a reporting waiver applies.
    • Externally set rates and thresholds — the countercyclical buffer rate, for instance.

    parameters MAY be empty, and is empty for a module whose Operations read no Parameter.

    3.10 operations¶

    The Operations of this document.

    • Member name: the Operation code, e.g. "EGDQ_0648".
    • Member value, the Operation Object:
    Member Type Notes
    code String MUST equal the member name.
    version_id Integer Identifier of this Operation version within the content the Producer generated it from. See the note below.
    expression String The DPM-XL source expression. Informative; see §4.1.4.
    root_operator_id Integer OperatorID of the root Node. Redundant; see §4.2.
    ast Object Root Node of the tree (§4).
    severity String "error", "warning" or "info".
    from_submission_date String ISO 8601 date. The first submission date from which this Operation applies, which is a different clock from the reference-period window of dates (§3.4): a rule added late in a module version's life applies only to submissions from this date onward, including submissions about earlier reference periods. See §2.6. 
    "EGDQ_0052_0": {
  "version_id": 2071,
  "code": "EGDQ_0052_0",
  "expression": "with {r0010-0110, default: 0}: if {tF_32.04.a, c0010} > 0 then {tF_32.04.b, c0030} > 0 endif",
  "root_operator_id": 30,
  "ast": { "class_name": "CondExpr", "condition": { … }, "then_expr": { … } },
  "from_submission_date": "2026-03-31",
  "severity": "error"
}

    Identifiers are only as good as the shared provenance

    code and version_id identify the Operation within the content the Producer generated it from, which need not be — and in general is not — the validation set of a DPM database. A Consumer MUST therefore treat both members as identifiers local to the document and its generation line, and MUST NOT join on them against a DPM database. The structural members can be checked that way; the rule identifiers cannot. See §5.7.2.

    How a Producer obtains the value is outside the scope of this part: it may be an OperationVID carried over from a DPM database, or a number derived by other means where there is no database to carry one over from. The format requires only that it is an Integer, and that it is stable for a given Operation version within one generation line. It is precisely because the value may or may not be a DPM identifier, while always looking like one, that joining on it is forbidden.

    No format is imposed on the Operation code. Codes in circulation include EGDQ_0052_0, EGDQ_0071a and EGDQ_0928_P04.01, and also bare decimal numbers such as "42", so no lexical pattern may be assumed. Consumers MUST treat the code as an opaque String and MUST NOT parse it.

    Every Operation in this section is a validation and is active for this module version (§2.6). The root Node MUST be an Operator Node, and the Operation MUST yield Boolean (a Scalar Boolean, or a Recordset of Boolean values where the tree expands to several Position Indices).

    severity applies to every failing result of the Operation. Where the tree expands to several Position Indices, each index yields an independent result and each failing index is reported independently, all at the same severity.

    The three severities are error, warning and info, in decreasing order of consequence, and a Consumer MUST implement all three. info is a reportable observation, not a defect; a Consumer MUST distinguish it from warning rather than folding the two together, and MUST NOT treat any severity as grounds for rejecting a submission on its own.

    Consumers MUST NOT evaluate an Operation against a submission dated before from_submission_date.

    3.11 dependency_information¶

    Member Type Presence Notes
    intra_instance_validations Array of String REQUIRED Operation codes evaluable from a single instance of this module version.
    cross_instance_dependencies Array of Object REQUIRED Dependency groups, below. MAY be empty.
    alternative_dependencies Array of Array of String REQUIRED Groups of interchangeable modules (§3.11.1). MAY be empty.

    All three members are REQUIRED. alternative_dependencies MUST be emitted as an empty array where no alternatives exist, not omitted — unlike an OPTIONAL member, whose absence would carry meaning (§4.1.3).

    Consumers MUST reject a document containing an unrecognised member of dependency_information (§5.3, rule V-27).

    Each entry of cross_instance_dependencies:

    Member Type Notes
    modules Array of Object The foreign module versions required. MUST be non-empty.
    affected_operations Array of String Operation codes requiring them. MUST be non-empty.
    from_reference_date String ISO 8601 date. First reference date the dependency holds for.
    to_reference_date String Last reference date, inclusive; the empty string if open-ended (§3.4).

    Each entry of modules:

    Member Type Notes
    URI String Taxonomy module URI. MUST be either a member name of dependency_modules or the root URI of this document (§3.11.3).
    module_version String Version of that module.
    ref_period String Reference period of the required instance, relative to the instance under validation. 
    "cross_instance_dependencies": [ {
  "modules": [ { "URI": "http://www.eba.europa.eu/.../mod/corep_of",
                 "module_version": "3.1.0", "ref_period": "T" } ],
  "affected_operations": [ "EGDQ_0670", "EGDQ_0671", "EGDQ_0672", "EGDQ_0786" ],
  "from_reference_date": "2023-06-30",
  "to_reference_date": "2025-03-30"
} ]

    ref_period MUST match T, T-<n><p> or T+<n><p>, where <n> is a positive integer and <p> is a period indicator as defined for TimeShiftOp (§4.27). T denotes the same reference period as the instance under validation; T-1A denotes one year earlier, T+1Q one quarter later.

    A shifted ref_period occurs only on a self-dependency. Where the entry names another module version, ref_period MUST be T: an Operation compares this instance against another module's instance for the same reference period, and no Operator selects from a foreign module at a shifted period. The shifted forms belong to §3.11.3, where TimeShiftOp gives them their use; a Consumer MUST accept a shift in either direction there and MUST NOT assume the backward form.

    Forward shifts are not a modelling error. COREP_LR declares a T+1Q self-dependency because a leverage-ratio figure is checked against the following quarter's submission; the Operation simply cannot be evaluated until that instance exists.

    intra_instance_validations and cross_instance_dependencies MUST cover operations exhaustively and MUST NOT overlap (§5.3, rule V-14): every Operation appears in one member or the other, and none in both. Documents violating this are in circulation, and §5.7.1 records the failure mode — a cross-module Operation whose dependency entry, and hence whose foreign table structure, was never emitted.

    3.11.1 alternative_dependencies¶

    Each element is a group of two or more taxonomy module URIs that are mutually exclusive sources for the same data: a reporter files one of them and never more than one, and a dependency naming any member of the group is satisfied by whichever member was filed.

    "alternative_dependencies": [
  [ "http://www.eba.europa.eu/eu/fr/xbrl/crr/fws/finrep/4.2/mod/finrep9",
    "http://www.eba.europa.eu/eu/fr/xbrl/crr/fws/finrep/4.2.1/mod/finrep9dp" ]
]

    Why a group arises. The same table exists in more than one module. Where an Operation needs such a table, the module that supplies it is not determined by the rule but by which of those modules the reporter files, so the dependency must name every candidate. In AE 1.4.0 all seventeen required tables — F_01.01, F_04.01, and so on — exist in both finrep9 3.3.0 and finrep9dp 1.1.0, with identical Variable sets in each. alternative_dependencies records that those two modules are the alternatives.

    Every URI in every group MUST be a member name of dependency_modules, and a group MUST have at least two members (§5.3, rule V-28). A document MAY declare several groups, and a group MAY have more than two members, though a pair is the usual case.

    3.11.2 Conjunction, and Declared Alternation¶

    Three levels of logic apply, and the distinction is normative:

    • The modules of a single entry are conjunctive. Every module version listed MUST be available for the Operation to be evaluated.
    • Several entries naming the same Operation are conjunctive by default: each entry states a separate requirement, and all of them MUST be satisfied.
    • Entries whose modules belong to one alternative_dependencies group are mutually exclusive alternatives: exactly one of them can ever be satisfied, and satisfying that one satisfies the requirement.

    Alternation is never inferred. Consumers MUST NOT treat repeated affected_operations across entries as evidence of it; a genuine conjunction wrongly read as alternation causes an Operation to be evaluated against incomplete data.

    In AE 1.4.0, eleven Operations appear in two entries — one naming finrep9 3.3.0, the other finrep9dp 1.1.0 — and alternative_dependencies declares those two URIs a group. Requiring both would demand that an institution file both FINREP variants, which no reporter does.

    A Consumer MUST evaluate an Operation listed in cross_instance_dependencies when, for every entry naming it whose window contains the instance's reference date, each module of that entry's modules is available for the required ref_period — counting a module as available when any member of its alternative_dependencies group is available. Otherwise the Operation is not evaluable against the submission in hand, and a Consumer MUST NOT evaluate it. How that is then reported is the Consumer's own concern (§1.1); what this part requires is that the absent data is not silently treated as null and the Operation thereby passed or failed.

    Because the members of a group are mutually exclusive, a Consumer SHOULD expect exactly one of them and MAY treat the presence of two as an error in the submission rather than in the Script Document.

    An Operation MUST be evaluated once regardless of how many entries name it. Which instance supplies a given Operand is determined by the table of the VarID (§4.3), not by entry order; where alternatives are present, by whichever member of the group was filed. Where the alternatives declare the same tables with the same Variables, as in AE 1.4.0, the loading path is identical whichever was filed.

    Severity may depend on which alternative was filed

    The alternatives are interchangeable as sources of data, but not necessarily as scopes. DPM-ML attaches severity to a scope covering a combination of module versions, so an Operation may be an error against one alternative and a warning against another. This document carries a single severity per Operation (§3.10) and cannot express the difference — a limitation that falls on the module which depends on the group, not on the alternatives themselves. See §5.7.2.

    3.11.3 Self-Dependencies¶

    An entry of modules whose URI equals the root URI of the document (§3.1) is a self-dependency: the Operation requires another reference period of the same module version. Such an entry MUST have a ref_period other than T, and MUST NOT appear in dependency_modules, whose purpose is to describe foreign structure that the document does not already carry.

    Self-dependencies are how TimeShiftOp (§4.27) is declared. An Operation comparing a figure against its value one year earlier produces an entry such as:

    { "modules": [ { "URI": "http://www.eba.europa.eu/.../mod/finrep9",
                 "module_version": "3.3.0", "ref_period": "T-1A" } ],
  "affected_operations": [ "EGDQ_1226", "EGDQ_1245" ],
  "from_reference_date": "2026-03-31",
  "to_reference_date": "2027-09-29" }

    The T-1A self-dependency is the declarative counterpart of the TimeShiftOp in the tree of each affected Operation.

    A shifted ref_period is confined to this case: every entry naming another module version carries T (§3.11, rule V-16). A temporal shift is something an Operation does to its own module's data, so there is no construct that would produce a shifted foreign entry.

    3.12 dependency_modules¶

    Structural information for the foreign modules named in cross_instance_dependencies.

    • Member name: the taxonomy module URI of the foreign module.
    • Member value:
    Member Type Notes
    tables Object Table dictionary, in the form of §3.6, restricted to tables of the foreign module that cross-module Operands reference.
    variables Object Data Type dictionary, in the form of §3.5. See the note below. 
    "dependency_modules": {
  "http://www.eba.europa.eu/.../mod/corep_of": {
    "tables":    { "C_01.00": { "variables": { "84817": "m" }, "open_keys": {} } },
    "variables": { "84817": "m", "32026": "m", "32024": "m", "32025": "p" }
  }
}

    Both members are REQUIRED.

    variables is not restricted to the foreign module

    Contrary to what the nesting suggests, variables here lists the Data Types of all Variables referenced by the Operations that depend on this foreign module — those of the local module included. In the example above only 84817 belongs to C_01.00 in COREP_OF; the rest are Variables of the local module's own tables. An entry will in general carry identifiers that its own tables do not, and a large share of them will be local. The member is a convenience dictionary for evaluating the affected Operations, not a description of the foreign module.

    Consumers MUST NOT infer module membership from this member; tables is the authority for foreign structure. Producers MUST populate it as specified so that the union of variables and each entry's tables[*].variables covers every datapoint reachable from the affected Operations.

    Every member name of dependency_modules MUST occur as some modules[*].URI, and every modules[*].URI other than the root URI MUST be a member name here (§5.3, rule V-16). The two sides of the correspondence are therefore always in step: a Consumer that finds a URI it cannot resolve, or an entry nothing refers to, has a malformed document.
