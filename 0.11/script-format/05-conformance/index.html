    5 Conformance¶

    5.1 Producer Requirements¶

    A conforming Producer MUST:

    1. Emit exactly one Script Document per module version, containing every Operation whose scope for that module version is active, and no Operation whose scope is inactive.
    2. Resolve every with context into every VarID Node, so that no Node depends on an enclosing context (§2.3).
    3. Expand every range, wildcard and enumerated selection into explicit Datapoint References, carrying each cell's resolved coordinates on every axis the selection did not pin, and assigning Position Indices on the row, column and sheet axes as x, y and z only where the axis varies (§2.4, §4.3.2).
    4. Emit a document satisfying every rule of §5.3.
    5. Keep expression, root_operator_id and ast mutually consistent (§4.1.4, §4.2).
    6. Refrain from emitting any construct listed as Unassigned in §5.4.
    7. Declare in parameters every Module Parameter that any ParameterRef reads, with the type that ParameterRef carries, and emit each ParameterRef.default explicitly — the declared default, or null (§3.9, §4.8.1).
    8. Emit only preconditions that yield a Scalar Boolean (§3.7.1), and declare the Variables a precondition selects in the same dictionaries as those of an Operation.
    9. Emit a cross_instance_dependencies entry for every Operation that selects from a table of another module version or another reference period, and a dependency_modules entry for the structure of each such module. This is the requirement most often missed in practice; see §5.7.1. Producers SHOULD regenerate all documents of a framework together for a given dpm_release, so that cross-module dependencies are mutually consistent. Where they do not — a module version need only be regenerated when it changes, so documents held together may name different releases (§3.3) — each document's dpm_release MUST still record the release it was actually generated from.

    5.2 Consumer Requirements¶

    A conforming Consumer is one that reads a Script Document correctly. What it then computes is governed by the Operators and Information Model parts, and what it reports is its own concern (§1.1); neither is a requirement of this part.

    A conforming Consumer MUST:

    1. Dispatch solely on class_name, and jointly on class_name and op where a class carries several Operators (§4.1.1, §4.2).
    2. Reject a document containing an unrecognised Module Object member, an unrecognised class_name, or an unrecognised op for a recognised class.
    3. Evaluate ast, never expression (§4.1.4).
    4. Honour the distinction between an absent OPTIONAL member and an explicit null (§4.1.3) — in particular, treat an absent CondExpr.else_expr as the one-armed form (§4.26).
    5. Read each Datapoint Reference's position from the entry itself, never from the VarID-level coordinates, which record only what the selection pinned (§4.3.2).
    6. Resolve Data Types from variables, tables[*].variables, precondition_variables and dependency_modules[*] only, never by inference from a value found in an instance.
    7. Determine which Variables to load from each table of an instance from tables[*].variables, never by collecting the table and datapoint values found in operations (§3.6).
    8. Resolve Component codes only against the document in hand — the open_keys of §3.6, after any RenameClauseOp (§4.24) — together with the Fact Component f and the three reserved contextual codes entityID, refPeriod and baseCurrency, which no open_keys declares (§4.7.2, §4.23).
    9. Resolve every Module Parameter an Operation reads in the order supplied binding, then that reference's default, then null (§3.9.2, §4.8.2). The third step is a value, not a failure: a Consumer MUST NOT refuse to load a document, or set an Operation aside, because a Parameter is unbound.
    10. Apply the applicability rules: reference date within dates (§3.4), submission date at or after from_submission_date (§3.10), and, for a cross-instance Operation, every in-window dependency entry satisfied — counting a module as available when any member of its alternative_dependencies group is (§3.11.2).
    11. Accept both spellings of an open-ended upper bound: null in dates.to, the empty string in to_reference_date (§3.4).

    Consumers MAY cache resolved Node results, since Nodes are context-free (§2.3). Consumers MUST NOT cache across documents keyed on codes, since codes are version-scoped (§3.6).

    What is deliberately not required here

    Earlier drafts of this part also told a Consumer how to combine Operands across Position Indices, how to treat interval on a non-numeric Operand, when to skip an Operation whose precondition is false, and which outcome categories to report. The first three are semantics, specified in the Operators and Information Model parts and identical whether an Operation reaches an engine as a document or as surface syntax; restating them here could only duplicate or contradict them. The fourth is output, which this part does not standardise (§1.1).

    A Consumer that satisfies the eleven requirements above has read the document as intended. Whether it then evaluates it correctly is a question about the Operators part, and this part defers to it entirely (§1.3).

    5.3 Structural Validation Rules¶

    A Script Document is valid if and only if all of the following hold. These rules are mechanically checkable without reference to any external artefact, and a Producer MUST NOT publish a document that violates any of them.

    # Rule
    V-1 The root object has exactly one member, whose name is an absolute URI.
    V-2 The Module Object has all fourteen REQUIRED members (§3.2) and no other member; format_version matches MAJOR.MINOR (§3.2.1).
    V-3 For every entry of operations and preconditions, code equals the member name, and the entry carries exactly the members specified in §3.10 and §3.7 respectively.
    V-4 For every Operation Object whose root Node encodes a DPM-ML Operator, root_operator_id equals that OperatorID per §4.2.
    V-5 Every Node has a class_name from §4.1.2, and carries only the members specified for that class.
    V-6 Every VarID axis is in exactly one of the four states of §4.3.2; no partial placement occurs; where an entry carries a coordinate whose axis is also fixed at the VarID level, the two are equal; at least one axis is not Not applicable.
    V-7 Within every VarID, data is non-empty, every datapoint is non-null, all index components are positive integers, and all Position Indices are pairwise distinct.
    V-8 variables equals the union of tables[*].variables.
    V-9 Every datapoint of every VarID in operations or preconditions appears in variables if the VarID's table is a member name of tables, and otherwise in the variables or tables[*].variables of some dependency_modules entry.
    V-10 Every table of every VarID in operations or preconditions is a member name of tables or of some dependency_modules[*].tables.
    V-11 The key sets of variables and precondition_variables are disjoint, and every value of precondition_variables is "b".
    V-12 Every precondition ast has idx(ast) = ∅ under §4.1.5, so it does not vary on any axis (§3.7.1). Every variable_id of every PreconditionItem, wherever it occurs, appears in precondition_variables.
    V-13 Every code in affected_operations, in both preconditions and cross_instance_dependencies, is a member name of operations; every such array is non-empty.
    V-14 intra_instance_validations and the union of all cross_instance_dependencies[*].affected_operations cover the member names of operations exhaustively and do not intersect each other. An Operation MAY appear in several cross_instance_dependencies entries (§3.11.2).
    V-15 Every operand_reference_id denotes exactly one (table, datapoint, row, column, sheet) combination throughout the document. It need not be unique (§4.3.4).
    V-16 Every modules[*].URI is a member name of dependency_modules or the root URI; every member name of dependency_modules occurs as some modules[*].URI; every self-referencing entry has a ref_period other than T, and every entry naming another module has ref_period T; every ref_period matches T, T-<n><p> or T+<n><p> (§3.11.3).
    V-17 Every Operator's operands combine under §4.1.5: one of them has an axis set containing every other's, and each ranges over exactly that operand's positions on the axes it shares.
    V-18 Every date member is a well-formed ISO 8601 calendar date, except that dates.to MAY be null and to_reference_date MAY be the empty string; and dates.from ≤ dates.to and from_reference_date ≤ to_reference_date hold wherever the upper bound is present and bounded.
    V-19 severity is "error", "warning" or "info".
    V-20 For every Constant, the JSON type of value corresponds to type_, "Date" is a well-formed YYYY-MM-DD string, and "Null" has value null (§4.4).
    V-21 Every BinOp with op: "in" has a Set or SetOp Node as right; every Set has a children array containing only Scalar or Constant Nodes, possibly empty (§4.6).
    V-22 Every Dimension Node occurs in one of the four positions of §4.7; every GroupingClause occurs as the grouping_clause of an AggregationOp; every AnalyticClause occurs as its analytic_clause. Checked in preconditions as well as operations.
    V-23 Every GroupingClause component is "r", "c", "s", or a Component code available on the operand — a member name of open_keys for the operand's table, or a to_component introduced by a RenameClauseOp between the table and the AggregationOp (§4.19).
    V-25 The root Node of every Operation Object is an Operator Node.
    V-26 Every dictionary in the document that mentions a given VariableID assigns it the same Data Type (§3.5).
    V-27 dependency_information has exactly intra_instance_validations, cross_instance_dependencies and alternative_dependencies, and no other member.
    V-28 Every group of alternative_dependencies has at least two members, every URI in it is a member name of dependency_modules, and no URI appears in two groups.
    V-29 Every value of parameters is one of the twelve type names of §3.9.1; every ParameterRef.code is a member name of parameters; every ParameterRef.param_type equals the declared type; every non-null ParameterRef.default has the JSON type its param_type requires — a bare item-signature String for "Item", and a JSON array of such values, possibly empty, for a Set type (§3.9, §4.8.1).
    V-30 Every AggregationOp has at most one clause present and non-null; rank has an AnalyticClause with window absent or null and a non-empty order_by; an AnalyticClause with a non-null window has a non-empty order_by, and its window has a frame_type of "data_points" or "range" with well-formed start and end bounds (§4.18, §4.20).
    V-31 Every SetOp has the arity its op requires — one for set_of, two for setdiff and symdiff, two or more for union and intersect; every SubstrOp has integer or null start and length; every RenameClauseOp has a non-empty clauses array whose from_component and to_component sets do not overlap; every DateConstructorOp carries year_node, month_node and day_node, and every AnnualiseOp its operand, fy_end and component (§4.14–§4.17, §4.24).
    V-32 Every dependency_modules entry has exactly tables and variables, and no other member (§3.12).

    Rules V-9, V-10 and V-23 resolve against dictionaries carried in the same document, so every rule above remains checkable from the document alone.

    V-24 is withdrawn

    An earlier version of this part carried a rule V-24, requiring VarID.default to agree with the Data Type of its datapoints and interval: true to appear only on a numeric selection. Both are constraints on what a selection may mean — a fallback of the wrong type and interval arithmetics over an enumeration are type errors, settled by the Information Model and the Operators part before a document is produced — and neither can be decided without knowing what a Data Type is for. They are therefore semantic analysis, not serialisation, and this part no longer states them (§1.1).

    The identifier is retired rather than reused, and the rules after it keep the numbers they had, so references to V-25 and beyond remain valid.

    5.3.1 Reference Validator¶

    A reference implementation of all 31 rules is published alongside this part: validate_script.py. It depends only on the Python standard library, requires neither the DPM database nor the taxonomy, and stands to this part as the .g4 files stand to the Grammar.

    python validate_script.py COREP_LE-3.3.0.json          # human-readable
python validate_script.py --json FINREP9-3.3.0.json    # machine-readable
python validate_script.py --quiet *.json               # exit code only

    It exits 0 when every document is valid, 1 on any violation, and 2 when a document cannot be read or parsed. Violations are grouped by rule identifier.

    The validator is a conformance aid, not the definition: where its behaviour and the rules above disagree, the rules prevail.

    One limitation is inherent rather than incidental. The Position Index set of a grouped AggregationOp depends on reported data (§4.1.5), so V-17 cannot be decided statically for any Operator above one. The validator counts these separately as not statically verifiable rather than passing them silently.

    5.4 Unassigned Constructs¶

    Three constructs have no encoding in this version of the specification. The first two are whole Operation types, not gaps in the expression language, and both need a design decision rather than an inference:

    • Calculations. Every Operation in a Script Document is a validation. DPM-ML defines Calculation as an Operation type (Information Model §5.1) and links calculated Variables through VariableCalculation (Information Model §5.4); neither has an encoding here. Persistent assignment, Operator 36 <-, is unassigned for the same reason: it is the Operator that writes a calculated result, so it has nothing to act on until Calculations are encoded. Encoding them requires more than a Node class — a document would have to say which Operations produce data, in what order they run, and how a produced Variable becomes available to the Operations that consume it.
    • Conditional severity. severity is a String on the Operation Object (§3.10). DPM-ML defines Conditional_severity as an Operation type whose result determines the severity of a failing case; there is no member for it, and adding one means deciding whether the severity-determining Operation is carried inline, referenced like a precondition, or resolved by the Producer before publication.

    The third is a single Operator:

    • Operator 34, node. It has no semantics anywhere in this specification — not in the Operators part, which describes rename (Operator 33) without ever mentioning node, and not in the Grammar. An earlier version of this part assigned it a JSON shape on RenameClauseOp so that a document using it would be recognised rather than rejected; that was a mistake, because a shape without a meaning cannot be implemented, and no document has ever carried it. RenameClauseOp now encodes Operator 33 only (§4.24).

    A Producer MUST NOT emit any of the three in any form. A Consumer encountering an unrecognised op value or class_name MUST reject the document (§5.2, requirement 2) rather than guess an interpretation. Assigning an encoding is a revision of this specification (§5.6); implementations MUST NOT anticipate one.

    5.5 Reserved Extension Points¶

    The following members and values are deliberately shaped to admit extension without a breaking change. Producers MUST NOT use them for any other purpose; Consumers MUST NOT assume the value this version assigns is the only one they will ever meet.

    Location Current Reserved for
    Scalar.scalar_type "Item" Other kinds of DPM object reference — Property, SubCategory.
    TimeShiftOp.reference_period "refPeriod" Any Date-typed Component as the temporal anchor, rather than only the instance's own reference period.
    AnnualiseOp.component "refPeriod" The same, on the same terms (§4.17).
    AnalyticClause.window.frame_type "data_points", "range" Further frame modes, e.g. groups (§4.20).
    Constant.type_ Integer, Number, Boolean, String, Date, Null Item-valued and date-time literals.
    modules[*].ref_period T, T±<n>{A,Q,M} Further period indicators.

    Two DPM-ML attributes have no slot and would require a new member: OperationNode.AbsoluteTolerance and OperationNode.RelativeTolerance. Were a tolerance ever authored, comparison Operators would need to carry it, and a Consumer built against this version would silently apply exact comparison instead — a wrong answer rather than a rejected document, which is the dangerous kind of gap. Producers MUST therefore treat a non-null tolerance in DPM-ML as a condition requiring a revision of this specification, not as a value to discard.

    5.6 Versioning¶

    This specification is versioned with the documentation set it belongs to. A change is breaking if a document valid under the previous version becomes invalid, or is validly interpreted differently. Assigning an encoding to an Unassigned construct (§5.4), or a new value at a Reserved Extension Point (§5.5), is not breaking for Producers but requires a Consumer update to be usable.

    Every Script Document carries the revision it was written to, in format_version (§3.2.1). A Consumer therefore always knows which rules a document was generated under, rather than having to infer it from which members happen to be present. A Consumer SHOULD also report the specification version it implements alongside its results, so that a mismatch is visible from both ends.

    format_version is MAJOR.MINOR. A MAJOR increment marks a breaking change under the rule above; a MINOR increment marks a change a Consumer built for an earlier MINOR of the same MAJOR can still read — a new value at a Reserved Extension Point (§5.5), an encoding assigned to an Unassigned construct (§5.4), or a requirement relaxed. Relaxing a requirement is never breaking for a Consumer, but it is for a Producer's expectations of one, which is why it moves MINOR rather than nothing at all.

    Why the member exists

    Earlier versions of this part carried no version member, on the reasoning that dpm_release plus the Consumer's own version determined compatibility. That reasoning does not survive contact with real documents. Two of them in circulation carry the same module_code and module_version — AE 1.4.0 — from two different Producers, and differ in whether parameters is present, in whether an AggregationOp carries analytic_clause at all, and in whether a VarID.data entry repeats the coordinate fixed at the VarID level. Nothing in either document said which convention it was written to; the only way to tell was to open it and look, and a Consumer meeting one could report only an unrecognised or missing member without being able to say which revision it had been handed.

    Adding the member is itself a breaking change under the rule above, and is the reason this version is 1.0.

    5.7 Known Gaps and Limitations¶

    This section is informative. It records two things an implementer will otherwise discover the hard way: a failure mode seen in documents already in circulation, and what a DPM database can and cannot be used to check a document against.

    Nothing here relaxes a rule. A document exhibiting §5.7.1 is invalid under §5.3, and a Producer MUST fix it at source.

    5.7.1 Incomplete cross-instance dependency information¶

    Documents are in circulation in which some Operations appear in neither intra_instance_validations nor any cross_instance_dependencies entry, contrary to rule V-14. Every such Operation is a cross-module rule: it selects from a table of another module version, and because its dependency entry was never emitted, neither was that module's structure in dependency_modules.

    One omission therefore shows up as several apparently separate failures:

    Rule Symptom
    V-14 The Operation is in neither dependency group.
    V-10 Its VarID names a table that is in neither tables nor dependency_modules[*].tables.
    V-9 Its datapoints are consequently in no Data Type dictionary.
    V-13 A precondition may gate an Operation absent from operations altogether.

    The undeclared tables are ordinary tables of the other module — not stale or misspelled codes; they exist in the DPM release the document names. What is missing is the declaration, not the table.

    A Consumer MUST NOT guess. An Operation whose VarID names an undeclared table cannot be resolved — its Data Types are absent too — and MUST NOT be evaluated as though the missing table held no data.

    The failure is confined to the dependency section. Where an entry does exist it is complete, and the correspondence between dependency_modules and modules[*].URI holds (V-16), so a Consumer can rely on what is declared and need only handle what is missing.

    5.7.2 What a DPM database can and cannot confirm¶

    A Script Document has two halves, and only one has a counterpart in a DPM database. The distinction is worth stating because the natural assumption — that a document can be checked against the DPM it was generated from — is half right, and the wrong half fails silently.

    The structural half does correspond, exactly. A datapoint, a table version code, a Data Type code and a filing-indicator identifier are all DPM objects, and each resolves: the tuple (table, row, column, sheet) of a Datapoint Reference identifies a TableVersionCell whose Variable is that entry's datapoint, reading an axis the document leaves open as the DPM's r*, c* or s*. This is a strong check — it exercises range expansion, coordinate resolution and Variable assignment at once — and it is the right way to check a document suspected of being malformed.

    The validation half does not correspond, and is not meant to. code, version_id and operand_reference_id identify Operations and operand occurrences within the content the Producer generated from, which need not be the validation set of any DPM database. Worse, all three fall in the same numeric or lexical ranges as their DPM namesakes, so a join appears to succeed and returns an unrelated rule. A Consumer or tool MUST NOT join on them (§3.10, §4.3.4).

    This is the format doing its job rather than a shortcoming. §1.2 exists so that an engine needs no DPM at run time: an Operation's tree, coordinates, Data Types and applicability are all in the document. A database can confirm the structure a document asserts; it cannot confirm the rules, because the rules are not in it.
