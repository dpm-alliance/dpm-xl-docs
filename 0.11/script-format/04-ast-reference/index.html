    4 Abstract Syntax Tree Reference¶

    4.1 Common Rules¶

    4.1.1 The class_name Discriminator¶

    Every Node MUST be a JSON object carrying a class_name member whose value is a String drawn from the closed set in §4.1.2. class_name is the sole discriminator: a Consumer MUST determine a Node's interpretation from class_name alone, and MUST reject a document containing an unrecognised value.

    A Node MUST NOT carry any member other than those specified for its class.

    4.1.2 Node Inventory¶

    Twenty-five classes are defined. The OperatorID column gives the DPM-ML Operator identifiers the class encodes; — means the class encodes no DPM-ML Operator (see §4.2).

    class_name Kind OperatorID Section
    VarID Operand — resolved data selection — §4.3
    Constant Operand — literal — §4.4
    Scalar Operand — DPM item reference — §4.5
    Set Operand — set of items — §4.6
    Dimension Operand — Component reference — §4.7
    ParameterRef Operand — Module Parameter reference — §4.8
    PreconditionItem Operand — filing indicator — §4.9
    ParExpr Operator — parenthesised expression 37 §4.10
    UnaryOp Operator — one operand 1, 4, 6, 17, 24 §4.11
    BinOp Operator — two operands 2, 3, 5, 8, 13–16, 18–23 §4.12
    ComplexNumericOp Operator — n-ary numeric 7, 9 §4.13
    SetOp Operator — set construction and algebra — §4.14
    SubstrOp Operator — substring extraction — §4.15
    DateConstructorOp Operator — date construction — §4.16
    AnnualiseOp Operator — annualise — §4.17
    AggregationOp Operator — aggregation 11, 12, 26, 27 §4.18
    GroupingClause Clause — grouping specification 35 §4.19
    AnalyticClause Clause — analytic window specification — §4.20
    WhereClauseOp Operator — where clause 28 §4.21
    SubClauseOp Operator — sub clause 38 §4.22
    GetClauseOp Operator — get clause 29 §4.23
    RenameClauseOp Operator — rename clause 33 §4.24
    FilterOp Operator — filter 31 §4.25
    CondExpr Operator — if-then-else 30 §4.26
    TimeShiftOp Operator — time_shift 32 §4.27

    The set is closed. A Consumer MUST implement every class in it, and MUST reject a class_name outside it (§4.1.1).

    4.1.3 Absent Members Versus null¶

    The two conventions carry different meanings and MUST both be honoured:

    • Where a member is marked OPTIONAL, absence is significant and the member MUST be omitted rather than set to null. This applies to VarID.default, to the axis members of VarID and its entries, and to CondExpr.else_expr.
    • Where a member is marked nullable, it MUST be present, with null where it carries no value. This applies to AggregationOp.grouping_clause, AggregationOp.analytic_clause, AnalyticClause.window and ParameterRef.default.

    The asymmetry is normative. Consumers MUST NOT treat an absent nullable member as null, nor an explicit null as an absent OPTIONAL member.

    CondExpr.else_expr is the member most likely to be mishandled, because it is the one place where a semantically meaningful absence is encoded by omission rather than by null. A one-armed conditional is the common case, so a Consumer that treats the member as nullable will misread ordinary documents (§4.26).

    4.1.4 Status of expression¶

    expression (§3.10) is a DPM-XL expression that MUST be semantically equivalent to ast.

    It is nonetheless informative. Consumers MUST NOT parse it, and MUST NOT derive any part of the evaluation from it. Where expression and ast disagree, ast prevails. Its purpose is human review, traceability to the DPM-ML Expression column, and diagnostics.

    4.1.5 Position Index Algebra¶

    Let idx(N) denote the set of Position Indices produced by evaluating Node N (§2.4). Then:

    Node idx
    VarID The set of (x, y, z) triples of its data entries.
    Constant, Scalar, Set, Dimension, ParameterRef, PreconditionItem ∅ — Scalar; broadcast over any index set.
    ParExpr, UnaryOp, SubstrOp idx of the operand.
    BinOp, ComplexNumericOp, CondExpr The combined index set, per the rule below.
    AggregationOp ∅ when both clauses are null; with a GroupingClause, one index per distinct group; with an AnalyticClause, idx of the operand.
    WhereClauseOp, SubClauseOp, FilterOp idx of the operand or selection; membership is narrowed, indices are preserved.
    GetClauseOp idx of the operand; the Component value replaces the Fact, positions are unchanged.
    SetOp ∅ — the result is a Scalar Set, which carries no Components and no positions.
    RenameClauseOp, TimeShiftOp idx of the operand.

    Combination rule. Position Indices stand in for the Key Components that align Records in the Information Model (§2.4), so operands combine the way Recordsets do: by natural join on the axes they share. An axis present in one operand and absent from another is not a mismatch — the operand lacking it broadcasts along it.

    Write axes(S) for the set of axes on which the indices of S carry a component, and S↓A for the projection of S onto the axes A. For an Operator over operands N₁ … Nₙ, let S = { idx(Nᵢ) : idx(Nᵢ) ≠ ∅ }.

    1. If S is empty, the result is a Scalar.
    2. Otherwise there MUST be a member M of S with axes(T) ⊆ axes(M) for every T in S. M is the widest operand, and the result carries idx = M.
    3. Every T in S MUST satisfy M↓axes(T) = T↓axes(T) — on the axes it does have, it must range over exactly the positions the widest operand ranges over.
    4. An Operator meeting 2 and 3 is combined by joining each operand's Record to every index of M that agrees with it on axes(T), producing one result per index of M.
    5. Otherwise the Operator is ill-formed. Producers MUST NOT emit it, and rule V-17 rejects it. A Consumer MUST NOT evaluate it over the intersection, the union, or a positional truncation of the operand index sets: an ill-formed Operator has no result, and inventing one silently converts a document defect into a validation outcome.

    Two familiar shapes are special cases and need no separate rule:

    • Broadcast of a single value. An operand whose one index is (–, –, –) has axes = ∅, so condition 3 is vacuous and it broadcasts across every index of M. This is by far the commonest departure from equal index sets.
    • Equal index sets. Where every operand has the same axes, condition 3 reduces to equality, and the Operator combines index by index.

    The general case does occur. In EGDQ_0379 of COREP_OF 3.1.0,

    with {tC_14.01, s*}: if isnull({(c0460, c0470)}) then {c0440, default: 0} <= 12.5 * sum({(c0310, … , c0420), default: 0}) endif

    the condition ranges over two columns and six sheets — twelve indices on (y, z) — while {c0440} ranges over the six sheets alone, six indices on (z). Their z sets are identical, so the six-index operand joins on z and broadcasts along y, and the Operation yields twelve results: for each sheet, one check per column tested. The sum is a full reduction and contributes no index at all.

    Reading the index as an opaque triple instead of as a set of axis components would reject this Operation as a cardinality mismatch. That reading is wrong: it is the axes, not the arity, that must line up.

    Case 5 is what a genuine mismatch looks like — two ranges over the same axis of unequal extent, such as a ten-row range compared against an explicit twelve-row list. Silently truncating is the principal way two engines can disagree while both appearing to succeed, which is why it is prohibited rather than defined.

    Index identity. Two indices are equal when their x, y and z components are pairwise equal, an absent component being equal only to an absent component. An index component MUST be a positive integer, and indices within one VarID MUST be distinct.

    4.2.1 Operators With No OperatorID¶

    The DPM-ML Operator table is narrower than the language. The Operators part specifies a further twenty Operators that the table does not list, and each has an encoding here; a Consumer MUST implement them all:

    op Encoding Semantics
    exp UnaryOp op: "exp" Operators §4.2.4 — exponential.
    ln UnaryOp op: "ln" Operators §4.2.5 — natural logarithm.
    log BinOp op: "log" Operators §4.2.7 — logarithm in a given base.
    power BinOp op: "power" Operators §4.2 — exponentiation.
    nvl BinOp op: "nvl" Operators §8 — substitutes right where left is null.
    & BinOp op: "&" Operators §9.2 — string concatenation.
    len UnaryOp op: "len" Operators §9.1 — string length.
    substr SubstrOp §4.15 — substring by start and length.
    year, semester, quarter, month, week, day UnaryOp with that op Operators §10.2 — date-component extraction.
    date DateConstructorOp §4.16 — a Date from three Integers.
    annualise AnnualiseOp §4.17 — scale to a full-year equivalent.
    avg AggregationOp op: "avg" Operators §7.6 — arithmetic mean.
    median AggregationOp op: "median" Operators §7.7 — median.
    rank AggregationOp op: "rank" §4.18, §4.20 — analytic rank over an ordered window.
    set_of SetOp op: "set_of" Operators §13.2 — the set of an operand's values.
    union SetOp op: "union" Operators §13.3 — set union.
    intersect SetOp op: "intersect" Operators §13.4 — set intersection.
    setdiff SetOp op: "setdiff" Operators §13.5 — set difference.
    symdiff SetOp op: "symdiff" Operators §13.6 — symmetric difference.

    The divergence follows from how a Script Document tree is built: from the DPM-XL expression, not by walking DPM-ML OperationNode rows. The encodable vocabulary is therefore the language's, not the Operator table's. rank alone is specified nowhere but here, in §4.18 and §4.20.

    A (class_name, op) pair is consequently the identity of an Operator in this format, and the OperatorID is a cross-reference available only for the subset the table covers.

    Consequently root_operator_id is well-defined only where the root Node encodes a DPM-ML Operator. Where it does, it MUST equal that OperatorID (§5.3, rule V-4 checks this): it is fully derivable from ast and is retained as a checksum, so a Producer MUST NOT emit a document in which the two disagree. A Consumer needs neither to verify it nor to read it — the root Node carries its own class_name and op, and those are what a Consumer MUST dispatch on. Because an Operation must yield Boolean (§3.10), the Operators that can appear at a root are in practice the comparisons, the logical Operators and if-then-else.

    Categories differ from Node classes

    The Node classes group Operators by arity and encoding shape, not by the categories used in the Operators part. min and max are ComplexNumericOp because they are n-ary; + appears as both UnaryOp and BinOp; in and nvl are BinOp although they are specified under Set and Numeric operators respectively. Consumers MUST dispatch on class_name and op jointly, never on op alone.

    4.3 VarID¶

    A resolved data selection. The Operand of the Selection Operator, with all ranges expanded and all context applied.

    4.3.1 Fields¶

    Member Type Presence Notes
    table String REQUIRED Table version code. MUST be a member name of tables (§3.6) or of some dependency_modules[*].tables (§3.12).
    row String OPTIONAL Row code, when the selection fixes the row axis.
    column String OPTIONAL Column code, when the selection fixes the column axis.
    sheet String OPTIONAL Sheet code, when the selection fixes the sheet axis.
    interval Boolean REQUIRED Interval arithmetics setting.
    default any OPTIONAL Fallback value for nulls. A JSON integer, number, boolean or string — a Date written YYYY-MM-DD, an Item as its signature. Absent means none.
    data Array REQUIRED Datapoint References. MUST be non-empty.

    Each entry of data is a Datapoint Reference:

    Member Type Presence Notes
    datapoint Integer REQUIRED VariableID. MUST be non-null and MUST appear in the applicable Data Type dictionary.
    operand_reference_id Integer REQUIRED Identifier of the resolved cell reference. See §4.3.4.
    row String OPTIONAL Row code of this cell, on every entry where the table has a row axis.
    column String OPTIONAL Column code of this cell, on every entry where the table has a column axis.
    sheet String OPTIONAL Sheet code of this cell, on every entry where the table has a sheet axis.
    x Integer OPTIONAL Row Position Index, when the row axis varies within the Operand.
    y Integer OPTIONAL Column Position Index, when the column axis varies.
    z Integer OPTIONAL Sheet Position Index, when the sheet axis varies.

    4.3.2 Axis Placement¶

    Coordinates and indices are placed by two independent rules. The distinction matters, and the two are easy to conflate:

    • A VarID-level coordinate records what the selection fixed, after with push-down (§2.3). It is present only where the source expression pinned that axis to a single code.
    • An entry carries the resolved coordinate of its own cell on every axis the table version has, except where that axis is already fixed at the VarID level, in which case repeating it is permitted but not required.
    • An index member is present exactly where the axis varies within the Operand, that is, where the entries carry more than one distinct code for it.

    Formally, for each axis independently — row/x, column/y, sheet/z — a VarID MUST be in exactly one of these states:

    State Coordinate on VarID Coordinate on entries Index on entries Distinct codes
    Fixed by selection present on every entry or on none; where present, equal to it absent from every entry 1
    Fixed, not pinned absent present on every entry absent from every entry 1
    Varying absent present on every entry present on every entry ≥ 2
    Not applicable absent absent from every entry absent from every entry 0

    Partial placement MUST NOT occur: an index on some entries only, an index without its coordinate, or a VarID-level coordinate that some entry contradicts. At least one axis MUST be in a state other than Not applicable.

    Producers disagree about the redundant coordinate

    In the Fixed by selection state alone, the entry coordinate repeats a value already fixed one level up. Both conventions are in circulation and neither is a defect: one Producer repeats it on every entry, another omits it throughout. Since a Consumer must read the entry first in the other three states, the rule that covers both is simply: take the coordinate from the entry, and where the entry does not carry it, from the VarID. Earlier versions of this part required the repetition; requiring it would invalidate documents that are otherwise correct, so it is now permitted instead.

    Within one document, whether an axis is Not applicable is a property of the table version, not of the individual Operand: every VarID over the same table agrees. Across documents it does not, because table versions differ.

    The Fixed, not pinned state is what a wildcard produces when it happens to resolve to one code. {tC_68.00.a, c0010, s*} writes s*, so nothing is pinned onto the VarID; where the sheet axis of that table has a single sheet, the entries all carry sheet: "0010" and no z. It arises most often on the sheet axis, for the simple reason that single-sheet tables are common. Consumers MUST NOT treat the VarID-level coordinate as the authority for an entry's position — the entry is — and MUST NOT infer from its absence that the axis varies.

    Worked example¶

    Take the Operand {tC_17.01.a, (r0060, r0160, …), c0080} — ten rows named explicitly, one column. The row axis varies and the column axis is fixed by the selection. Three of its ten entries:

    { "class_name": "VarID", "table": "C_17.01.a",
  "interval": true, "default": 0,
  "column": "0080",
  "data": [
    { "datapoint": 51416, "operand_reference_id": 50735, "x": 1, "row": "0060", "column": "0080" },
    { "datapoint": 51421, "operand_reference_id": 50744, "x": 2, "row": "0160", "column": "0080" },
    { "datapoint": 51420, "operand_reference_id": 50753, "x": 3, "row": "0260", "column": "0080" }
  ] }

    column appears twice over — once on the VarID because the selection fixed it, once on each entry because that is where the cell's own coordinates live. There is no y, because the column axis does not vary. sheet and z are absent throughout because C_17.01.a has no sheet axis.

    4.3.3 Constraints¶

    1. Indices within one VarID MUST be pairwise distinct (§4.1.5).
    2. A VarID referencing a table of a foreign module MUST occur only within an Operation listed in a cross_instance_dependencies entry naming that module (§3.11). A foreign selection with no such entry cannot be resolved; see §5.7.1.
    3. Where the Data Types of the datapoints of one VarID differ, the Operators applied to it must be admissible for all of them — a semantic condition, and one this part does not check.

    Which Data Types admit interval, and which values may serve as a default, are questions about what a selection means rather than about how it is written. They are settled where Data Types are defined, and this part neither restates nor validates them (§1.1).

    Both reference implementations resolve such a VarID's Data Type per-Record rather than once for the whole Recordset, and give that per-Record state a dedicated internal type, Mixed, undocumented here but present in both (dpmcore/src/dpmcore/dpm_xl/types/promotion.py, cve/Code/DataTypes/ScalarTypes.py:239). Applying an Operator to a Mixed operand checks and promotes types row by row instead of once. Where the Operator has a fixed result type regardless of its operands (a comparison always yields Boolean), the result of the whole Recordset is that type; where it does not (arithmetic, nvl, …), the result stays Mixed, carrying a per-Record type onward rather than collapsing to one. The practical consequence is that restriction 3 above is checked per Record rather than once for the whole selection — again a matter for the type system, noted here only because the encoding gives no hint that a VarID is of mixed type.

    4.3.4 Semantics¶

    The VarID denotes a Recordset containing, for each Datapoint Reference, the reported value of the identified Variable, positioned at its Position Index. Where the value is absent from the instance, default supplies the value if present; otherwise null treatment applies as specified in Information Model §4 Null handling. Where interval is true, values are treated as intervals per Operators §3.1.2.

    operand_reference_id carries no evaluation semantics. It identifies a resolved cell reference: within one document the identifier MUST stand in a one-to-one correspondence with the tuple (table, datapoint, row, column, sheet), and every Operand that selects that cell repeats the same identifier (§5.3, rule V-15).

    Two consequences follow, and both matter:

    • The identifier is not unique within the document. A Consumer MUST NOT use it as a primary key for an Operand occurrence, and MUST NOT assume that two entries bearing it belong to the same VarID, the same Operation, or the same Position Index — the same cell may be indexed differently in different Operands. Repetition is the normal case, not the exception, since rules routinely test the same cell.
    • It is not a key into a DPM database. The member is named after the DPM-ML OperandReference table, but DPM-ML assigns one identifier per operand occurrence, keyed on NodeID, whereas the values here are one per cell. The two numberings are unrelated, and because they occupy overlapping ranges a join will appear to succeed while returning the wrong row. A Consumer MUST NOT join on this member across the two artefacts. To check an entry against a DPM database, use its table, coordinates and datapoint (§5.7.2).

    Within the document it is the RECOMMENDED identifier for reporting a failure against a specific cell.

    The Operand {tF_25.01.a, r0120, (c0030, c0040)}, whose column axis varies over two codes:

    { "class_name": "VarID",
  "table": "F_25.01.a", "row": "0120", "default": 0, "interval": true,
  "data": [ { "datapoint": 433544, "operand_reference_id": 131100, "y": 1, "row": "0120", "column": "0030" },
            { "datapoint": 433422, "operand_reference_id": 131109, "y": 2, "row": "0120", "column": "0040" } ] }

    4.4 Constant¶

    A literal Scalar.

    Member Type Presence Notes
    type_ String REQUIRED "Integer", "Number", "Boolean", "String", "Date" or "Null".
    value Integer, Number, Boolean, String or null REQUIRED The literal.

    The JSON type of value MUST correspond to type_: "Integer" with a JSON integer, "Number" with a JSON number, "Boolean" with a JSON boolean, "String" with a JSON string, "Date" with a JSON string holding an ISO 8601 calendar date, YYYY-MM-DD, and "Null" with a JSON null.

    type_ is spelled with a trailing underscore. This is normative.

    A surface percentage literal has no type_ of its own: % divides by 100 before this Node is built, so 5% and the decimal literal 0.05 produce the identical Constant, with type_: "Number". Nothing on the wire distinguishes a value that was written as a percentage from one that was always a plain decimal; where that distinction matters it is carried by the Data Type of the Operand the value feeds (p, Percentage, §3.5), never by Constant itself.

    { "class_name": "Constant", "type_": "Integer", "value": 1 }
{ "class_name": "Constant", "type_": "Date", "value": "2011-01-01" }
{ "class_name": "Constant", "type_": "Number", "value": 0.05 }

    4.5 Scalar¶

    A reference to a DPM item, used as the right-hand operand of a comparison inside a clause condition, and as an element of a Set.

    Member Type Presence Notes
    item String REQUIRED The item QName, in prefix:localName form, e.g. "eba_GA:x1".
    scalar_type String REQUIRED "Item".

    scalar_type distinguishes the kind of DPM object referenced. "Item" is the only value this version of the specification assigns; §5.5 reserves the member for further kinds.

    The QName is not resolved within the document: the enumeration it belongs to is not serialised (§2.8). Consumers requiring the enumeration MUST obtain it from the taxonomy or the DPM.

    { "class_name": "Scalar", "item": "eba_GA:x1", "scalar_type": "Item" }

    4.6 Set¶

    A set literal — the right-hand operand of in, or the empty set compared against a SetOp result.

    Member Type Presence Notes
    children Array REQUIRED Elements of the set: Scalar Nodes (§4.5) or Constant Nodes (§4.4), not both. MAY be empty.

    Order is not significant. See Operators §13 Set Operators.

    A Set is homogeneous. Its elements are all Scalar — enumerated DPM items — or all Constant — literals of one primitive type. Both forms are in circulation and both are correct; what does not occur, and would not mean anything, is a set mixing an Item with a Number, since every Operator that consumes a set compares its elements against a single value.

    The class_name on each child is redundant, and will not survive

    A homogeneous set repeats its element kind on every child, and repeats scalar_type or type_ there too, when both belong to the set as a whole. The encoding that would say this once — scalar_type on the Set itself and bare values in children — is the one this format should have. It is not changed here because documents in circulation use the shape above and this version describes them; the redesign is tracked as future work.

    An empty children array is the encoding of the DPM-XL empty-set literal {}, and is not a defect. Its usual place is the right operand of an equality against a SetOp — the idiom for asserting that a set difference is empty:

    { "class_name": "BinOp", "op": "=",
  "left":  { "class_name": "SetOp", "op": "setdiff", "operands": [ … ] },
  "right": { "class_name": "Set", "children": [] } }

    { "class_name": "Set",
  "children": [ { "class_name": "Scalar", "item": "eba_RS:x1", "scalar_type": "Item" },
                { "class_name": "Scalar", "item": "eba_RS:x6", "scalar_type": "Item" } ] }

    4.7 Dimension¶

    A reference to a Component of the operand Recordset, by code.

    Member Type Presence Notes
    dimension_code String REQUIRED The Component code.

    Unlike VarID, a Dimension carries no numeric identifier; only the code is serialised.

    4.7.1 The three Component roles¶

    A Recordset has Components in three roles — Key, Fact and Attribute (Information Model §2.2.3) — and dimension_code reaches all three. The role is not encoded: it follows from the code, and a Consumer determines it by where the code resolves.

    Role How the code resolves Examples
    Key — open A member name of open_keys for the operand's table (§3.6), after any RenameClauseOp (§4.24). GCC, INC, LGS, qEEA
    Key — standard The axis tokens r, c, s. r, c, s
    Key — contextual The reserved identifiers refPeriod and entityID, latent in every Recordset and never declared. entityID
    Fact The single reserved code f. f
    Attribute The Property code of an Attribute Variable associated with the selected Variables. Not declared in the document — see below. baseCurrency (the only Attribute code in circulation)

    Two consequences a Consumer MUST honour:

    1. open_keys is not the whole vocabulary. A Consumer that resolves every dimension_code against open_keys alone will reject documents it should accept, because f, the axis tokens, the contextual identifiers and every Attribute code lie outside it. baseCurrency is common enough that such a Consumer fails almost at once.
    2. Producers MUST NOT declare an Open Key named f, r, c, s, refPeriod or entityID. These are reserved (Information Model §2.4.3), and a table declaring one would make its own Components unaddressable.

    4.7.2 Reserved contextual codes, and Attribute Components¶

    Three codes are contextual: they are present on every Recordset, are declared by no open_keys, and a Producer MUST NOT declare an Open Key with any of them.

    Code Data Type Meaning
    entityID String The reporting entity of the instance under validation.
    refPeriod Date The reference period of the instance under validation. Reached through GetClauseOp (§4.23) rather than as a Dimension.
    baseCurrency Item The currency a monetary fact is reported in. An Attribute Component rather than a Key Component, but contextual in the same way: always present, never declared.

    A dimension_code therefore resolves against exactly two things: the three codes above, and the open_keys of the operand's table (§3.6), after any rename (§4.24). A code that resolves against neither is a malformed document, and a Consumer MUST reject it (§5.2, requirement 2) exactly as it would an unrecognised class_name — not treat it as an Attribute reference and carry on. Nothing outside this list is inferred.

    What an implementation does when the reported instance does not carry a value for a code that does resolve is a different question, and not one for this part: that is a property of the data, not of the encoding (§1.1).

    Attribute Components in general arise when a selected Variable has an associated Attribute Variable, the name being the Property code of that attribute (Information Model §2.2.3.3). §3.6 declares a table's Variables and its Open Keys, but not its Attributes; baseCurrency is the only one that occurs, and it is covered above as a contextual code. Declaring Attributes generally would require a new member of tables[*], which this version does not define.

    4.7.3 Placement¶

    A Dimension Node occurs in four positions, and nowhere else:

    • within the condition of a WhereClauseOp (§4.21) or a SubClauseOp (§4.22) — the usual case, as the left of a comparison BinOp, or as the operand of not/isnull, or as the whole condition where it is the Boolean Fact Component f;
    • within the condition of a FilterOp (§4.25);
    • as the operand of a SubstrOp (§4.15);
    • directly as the condition of a WhereClauseOp or SubClauseOp, where the Component is itself Boolean — in practice f.
    { "class_name": "Dimension", "dimension_code": "baseCurrency" }

    refPeriod is the one reserved code that does not appear as a Dimension: it is reached through GetClauseOp instead (§4.23), because the Operations using it want its value in the Fact rather than a test on it.

    4.8 ParameterRef¶

    A reference to a Module Parameter declared in parameters (§3.9). It is the encoding of the Parameter Selection, Information Model §3.1 and Operators §3.1.1, Form 5, written {p_BM, string} or {p_threshold, number, default: 0} in surface syntax.

    Member Type Presence Notes
    code String REQUIRED Parameter code. MUST be a member name of parameters (§3.9).
    param_type String REQUIRED MUST equal the type declared in parameters for code, in the spelling of §3.9.1.
    default any OPTIONAL, nullable Fallback value for this reference. Absent and null both mean none is declared.

    param_type duplicates the declaration and is retained so that a Node remains self-describing (§2.3). A Consumer MUST reject a document where the two disagree (§5.3, rule V-29).

    Note the case difference between the two forms: the surface syntax spells the type in lower case (string, boolean, integer), while param_type and parameters use the initial-capital spelling (§3.9.1).

    4.8.1 default¶

    default is the fallback for this reference, and it is where a Parameter default lives — the surface syntax attaches it to the selection, not to the declaration, and so does this format. It is OPTIONAL and nullable, on the same terms as VarID.default (§4.3.1): the two members answer the same question in their respective domains, and this part draws no distinction between them. A Producer MAY omit the member or emit null where the selection declares no default; a Consumer MUST treat the two alike. This is the one place where an absent member and an explicit null are equivalent, and it is stated here because §4.1.3 makes the opposite the general rule.

    Any value of the declared type is admissible, including null, which is a value of every Data Type. For a Set type an empty set — [] — is admissible and distinct from null: it declares a default that is the empty set, where null declares no default at all.

    The encoding follows the three shapes the surface syntax admits in this position — a literal, an item reference, or a set literal — each mapped to the Node class this part already uses for it:

    param_type default encoding
    "Integer", "Number", "Boolean", "String", "Date" A JSON literal, related to param_type exactly as Constant.value is to Constant.type_ (§4.4): a JSON integer, number, boolean or string, with "Date" a YYYY-MM-DD string.
    "Item" A bare String: the item signature (the same value as a Scalar Node's item, §4.5), not a Scalar Node.
    "SetNumber", "SetInteger", "SetString", "SetDate", "SetBoolean" A JSON array of bare literals of the element type, not a Set Node.
    "SetItem" A JSON array of bare item-signature Strings, not a Set Node.

    A default is always a bare value or an array of them, never wrapped in the Scalar/Set Node this part defines for the same value elsewhere in the format: param_type already fixes the element type, so a wrapper would only repeat it, the same reasoning that makes SubstrOp.start a bare integer (§4.15).

    4.8.2 Semantics¶

    A ParameterRef evaluates to a Scalar for the six Scalar types, and to a Scalar Set for the six Set types. Either way it carries no Position Index, so idx(ParameterRef) = ∅ and it broadcasts over any index set it is combined with (§4.1.5).

    Its value is resolved in the three steps of §3.9.2 — supplied binding, then this reference's default, then null. The third step is ordinary null, not a failure: the Operation is evaluated with a null Parameter under the null treatment of Information Model §4.

    Using a Parameter changes the contract between the Operation and its execution environment (Information Model §3.1.4): an engine that cannot obtain bindings will still evaluate the document, but the results of the affected Operations will reflect a null where a value was intended. A Consumer SHOULD therefore report which Parameters it resolved and from where — binding or default — alongside its results, so that such an outcome is visible rather than silent.

    { "class_name": "ParameterRef", "code": "BM", "param_type": "String", "default": null }

    With a declared default, encoding {p_threshold, number, default: 0}:

    { "class_name": "ParameterRef", "code": "threshold", "param_type": "Number", "default": 0 }

    An item-typed default, encoding {p_ccy, item, default: [eba_CU:EUR]}:

    { "class_name": "ParameterRef", "code": "ccy", "param_type": "Item", "default": "eba_CU:EUR" }

    A set-typed default, encoding {p_ccys, set-item, default: {[eba_CU:EUR]}}:

    { "class_name": "ParameterRef", "code": "ccys", "param_type": "SetItem", "default": [ "eba_CU:EUR" ] }

    4.9 PreconditionItem¶

    A reference to a filing-indicator Variable — a Boolean Operand, and a Scalar for the purposes of §4.1.5.

    Member Type Presence Notes
    variable_id Integer REQUIRED VariableID. MUST be a member name of precondition_variables (§3.8).
    variable_code String REQUIRED The filing indicator code, which is the code of the template it governs, e.g. "C_28.00".

    A filing indicator is a distinct kind of Variable in DPM-ML, not a fact, which is why it is referenced by its own Node class and typed in its own dictionary (§3.8) rather than through a VarID. It carries no coordinates: an indicator is reported once per instance, not per cell.

    Semantics¶

    Evaluates to true when the instance under validation reports the corresponding filing indicator as true, and to false otherwise — including when the indicator is absent.

    Placement¶

    A precondition tree (§3.7) is where a PreconditionItem is expected. That is not, however, the converse of §3.7.1: nothing in this part reserves the class to preconditions or forbids a Validation from testing a filing indicator. A Consumer SHOULD evaluate the Node wherever a Boolean Operand is admissible, rather than rejecting the document on its position.

    { "class_name": "PreconditionItem", "variable_id": 395097, "variable_code": "C_28.00" }

    4.10 ParExpr¶

    An explicit parenthesisation, retained from the source expression.

    Member Type Presence Notes
    expression Node REQUIRED The parenthesised Node.

    ParExpr is semantically transparent: it evaluates to its expression and preserves its index set. It carries no precedence information, because precedence is already resolved by the tree structure.

    Producers MUST preserve the parenthesisation of the source expression so that expression (§3.10) can be reconstructed. A ParExpr MAY nest directly within another ParExpr, and MAY be the root Node of an Operation. Consumers MUST accept ParExpr at any position where a Node is permitted, and MUST NOT rely on its presence or absence.

    { "class_name": "ParExpr", "expression": { "class_name": "BinOp", "op": "or", … } }

    4.11 UnaryOp¶

    Member Type Presence Notes
    op String REQUIRED One of the fifteen values below.
    operand Node REQUIRED The operand.
    op Category Operand type Result Semantics
    +, -, abs Numeric Numeric Numeric Operators §4.2
    sqrt, exp, ln Numeric Numeric Number Operators §4.2
    isnull Comparison any Boolean Operators §5.10
    not Logical Boolean Boolean Operators §6
    len String String Integer Operators §9.1
    year, semester, quarter, month, week, day Time Date Integer Operators §10.2

    The six date-component extractors share one signature and differ only in the component returned (Operators §10.2.1), so they take one op value each on the same Node shape. sqrt, exp and ln are likewise unary numeric functions, alongside abs.

    Note that sqrt, exp and ln always yield Number, never Integer, even for an Integer operand (Operators §4.1); and that they reject Number Interval operands, so a Consumer MUST NOT apply interval arithmetics to them even where the operand VarID carries interval: true.

    A date-component extractor takes any Date-valued Node. The commonest is [get refPeriod], the reference period of the instance read as a Component (§4.23), since a reported Date Variable is comparatively rare.

    { "class_name": "UnaryOp", "op": "isnull",
  "operand": { "class_name": "VarID", … } }

    4.12 BinOp¶

    Member Type Presence Notes
    op String REQUIRED One of the symbols below.
    left Node REQUIRED Left operand.
    right Node REQUIRED Right operand.
    op Category Operand types Result Semantics
    +, -, *, / Numeric Numeric Numeric Operators §4.3
    power, log Numeric left Numeric; right a Numeric Scalar Number Operators §4.2.7
    nvl Conditional left any, right of left's type left's type Operators §8
    =, !=, <, <=, >, >= Comparison Comparable, of compatible Data Type Boolean Operators §5
    match Comparison left String; right a String Scalar pattern Boolean Operators §5.9
    in Set left item- or value-valued; right a Set or SetOp Boolean Operators §13
    and, or, xor Logical Boolean Boolean Operators §6
    & String String String Operators §9.2

    Additional constraints:

    1. Where op is "in", right MUST be a Set Node (§4.6) or a SetOp Node (§4.14).
    2. Where op is "and", "or" or "xor", both operands MUST yield Boolean. No further restriction applies inside a precondition tree: a precondition is an Operation tree and admits every Node class (§3.7.1).
    3. Where op is "match", right MUST be a Constant with type_: "String" holding a regular expression in Python syntax (Operators §5.9.1.5). The grammar admits only a literal in this position, so a Producer MUST NOT emit a selection or a ParameterRef there.
    4. Where op is "log", right is the base and MUST be a numeric Scalar; where it is "power", right is the exponent. Both are asymmetric, so a Consumer MUST NOT commute their operands.
    5. Operand index sets MUST combine per §4.1.5.

    power and log are binary numeric functions in the surface syntax — log(op, base), power(op, exponent) — rather than infix Operators, but their encoding is a BinOp like any other two-operand Operator: the Node classes group by arity and shape, not by surface form (§4.2).

    nvl is the null-substitution Operator: it yields left where left is non-null and right otherwise. It is a BinOp although the Operators part specifies it under Numeric Operators, and it has no DPM-ML OperatorID (§4.2.1). All nine occurrences guard an AggregationOp against an empty aggregation, as nvl(count(…), 0).

    Associativity is expressed by nesting: a + b + c is encoded as one BinOp whose left is another BinOp. Consumers MUST NOT assume a particular nesting direction.

    { "class_name": "BinOp", "op": ">=",
  "left":  { "class_name": "VarID", "table": "C_28.00", "column": "040", … },
  "right": { "class_name": "VarID", "table": "C_28.00", "column": "050", … } }

    4.13 ComplexNumericOp¶

    The n-ary numeric Operators min and max.

    Member Type Presence Notes
    op String REQUIRED "min" or "max".
    operands Array of Node REQUIRED MUST contain at least two Nodes.

    Operands MUST be numeric and MUST combine per §4.1.5. The result is the least or greatest operand value at each Position Index. These are the element-wise numeric Operators, distinct from the aggregate min_aggr and max_aggr (§4.18), which reduce a Recordset. Arities of 2, 3 and 7 occur.

    { "class_name": "ComplexNumericOp", "op": "max",
  "operands": [ { "class_name": "VarID", … }, { "class_name": "VarID", … } ] }

    4.14 SetOp¶

    Set construction and set algebra. The result is a Scalar Set as defined in Operators §13 — unordered, duplicate-free, null-free, carrying no Components — so idx(SetOp) = ∅ (§4.1.5).

    Member Type Presence Notes
    op String REQUIRED One of the five values below.
    operands Array of Node REQUIRED Arity per op, below.
    op Arity Meaning
    set_of exactly 1 The Scalar Set of the distinct non-null Fact values of its operand.
    union 2 or more Members of any operand.
    intersect 2 or more Members of every operand.
    setdiff exactly 2 Members of the first operand that are not members of the second.
    symdiff exactly 2 Members of exactly one of the two operands.

    The arities follow the surface syntax (Operators §13): union and intersect are variadic, setdiff and symdiff strictly binary because neither is associative.

    Semantics are those of Operators §13 Set Operators, which is authoritative. None of the three has a DPM-ML OperatorID (§4.2.1).

    An operand that is a Recordset rather than a Scalar Set is implicitly read as the set of its Fact values, exactly as if wrapped in set_of (Operators §13.1.5). It is what lets union and setdiff apply directly to a GetClauseOp without an intervening set_of: [get INC] moves the Key Component into the Fact (§4.23), and the set Operator then takes the set of those values. A Consumer MUST perform that implicit conversion rather than rejecting the operand.

    A SetOp occurs as the right of a BinOp in, or as an operand of an equality against a Set — usually the empty Set, to assert that a difference is empty:

    { "class_name": "SetOp", "op": "setdiff",
  "operands": [
    { "class_name": "SetOp", "op": "union", "operands": [ { "class_name": "GetClauseOp", … },
                                                          { "class_name": "GetClauseOp", … } ] },
    { "class_name": "GetClauseOp", … } ] }

    4.15 SubstrOp¶

    Substring extraction. idx(SubstrOp) = idx(operand).

    Member Type Presence Notes
    op String REQUIRED "substr".
    operand Node REQUIRED The String-valued Node to cut.
    start Integer or null OPTIONAL, nullable 1-based index of the first character taken. A plain JSON integer or null.
    length Integer or null OPTIONAL, nullable Number of characters taken. A plain JSON integer or null.

    start and length are encoded as bare JSON numbers (or null) rather than as Constant Nodes. If omitted or null, extraction begins at the first character and runs to the end of the string respectively (Operators §9.3.4). This is normative; a Consumer MUST NOT expect a Node here.

    Its characteristic use is cutting the institution's LEI out of the entity identifier — substr(entityID, 4, 20) — so the operand is typically a Dimension, though any String-valued Node is admissible. substr has no DPM-ML OperatorID (§4.1.2).

    { "class_name": "SubstrOp", "op": "substr",
  "operand": { "class_name": "Dimension", "dimension_code": "entityID" },
  "start": 4, "length": 20 }

    4.16 DateConstructorOp¶

    The date constructor: builds a Date from three Integer parts. See Operators §10.3.

    Member Type Presence Notes
    op String REQUIRED "date".
    year_node Node REQUIRED Integer-valued.
    month_node Node REQUIRED Integer-valued.
    day_node Node REQUIRED Integer-valued.

    The three parts are named members rather than an operands array, because they are positionally significant and not interchangeable — the same reason SubstrOp names start and length and TimeShiftOp names its arguments. The _node suffix distinguishes them from the same-named Operators of §4.11, year, month and day, which extract a part from a Date rather than supplying one. They are full Nodes, not bare integers: Operators §10.3.5 admits a Recordset in any of the three positions.

    No document in circulation uses this class, so the member names follow the only implementation that has them.

    All three MUST combine per §4.1.5, and the result carries the combined index set. This is the sanctioned way to obtain a Date from Integers, since Integer → Date is not a permitted cast.

    { "class_name": "DateConstructorOp", "op": "date",
  "year_node":  { "class_name": "UnaryOp", "op": "year", "operand": { … } },
  "month_node": { "class_name": "Constant", "type_": "Integer", "value": 12 },
  "day_node":   { "class_name": "Constant", "type_": "Integer", "value": 31 } }

    4.17 AnnualiseOp¶

    Scales each value to its full-year equivalent, given the month a financial year ends. See Operators §10.4.

    Member Type Presence Notes
    op String REQUIRED "annualise".
    operand Node REQUIRED The numeric Node to scale.
    fy_end Node REQUIRED Integer Scalar, the month (1–12) the financial year ends.
    component String REQUIRED Component code supplying each Record's reference date.

    fy_end is a Node because it is typically a ParameterRef — FINANCIAL_YEAR_END_MONTH is exactly this quantity — rather than a literal. It MUST evaluate to an Integer Scalar.

    component is a bare String naming a Component, on the same terms as GetClauseOp.component (§4.23) and TimeShiftOp.reference_period (§4.27): the surface syntax's third argument is a propertyCode, not an expression, so the encoding carries a code rather than a Node. "refPeriod" is the expected value.

    idx(AnnualiseOp) = idx(operand); fy_end is a Scalar and broadcasts.

    { "class_name": "AnnualiseOp", "op": "annualise",

    4.18 AggregationOp¶

    Member Type Presence Notes
    op String REQUIRED "sum", "count", "avg", "median", "max_aggr", "min_aggr" or "rank".
    operand Node REQUIRED The Recordset to aggregate.
    grouping_clause Node or null OPTIONAL, nullable A GroupingClause (§4.19). Absent and null both mean "no grouping".
    analytic_clause Node or null OPTIONAL, nullable An AnalyticClause (§4.20). Absent and null both mean "no analytic clause".

    Both clause members are REQUIRED and both are nullable; a Consumer MUST NOT treat either as optional (§4.1.3). They are mutually exclusive: at most one MAY be non-null (§5.3, rule V-30).

    op OperatorID Reduction Result type
    sum 26 Sum of the operand values. the operand's
    count 27 Number of Records, or the cardinality of a Scalar Set. Integer
    avg — Arithmetic mean of the operand values. Number
    median — Median of the operand values. Number
    max_aggr 11 Greatest operand value. the operand's
    min_aggr 12 Least operand value. the operand's
    rank — Ordinal position of each value within its window. Integer

    avg and median take the same Node shape as sum (Operators §7.6, §7.7) and admit a GroupingClause on the same terms. count differs in one respect: its operand MAY be a Scalar Set rather than a Recordset, in which case it returns the set's cardinality. A Scalar Set carries no Components to group by, so no grouping_clause accompanies it — a consequence of what a set is, specified in Operators §7.3, not an additional rule of this part.

    rank MUST take an AnalyticClause (and its window MUST be null). Other aggregate operators (sum, avg, count, min_aggr, max_aggr, median) MAY take an AnalyticClause instead of a GroupingClause.

    Semantics¶

    With both clauses null, the Operator reduces the whole operand to a single Scalar, and idx becomes ∅.

    With a GroupingClause, the operand is partitioned by the listed components and reduced within each partition, yielding one result per group. See Operators §7 Aggregate Operators.

    With an AnalyticClause, the Operator is not a reduction: it yields one value per input Record, computed over an ordered window or partition, and preserves the operand's index set. When op is rank, window MUST be null (rank cannot take a window frame). For other aggregate operators, a window MAY be specified.

    Null treatment follows Information Model §4 Null handling; note that a default on the operand VarID is applied before aggregation, so a fallback of 0 and no fallback are not equivalent.

    { "class_name": "AggregationOp", "op": "sum",
  "operand": { "class_name": "VarID", "table": "C_29.00", … },
  "grouping_clause": { "class_name": "GroupingClause", "components": [ "GCC" ] },
  "analytic_clause": null }

    4.19 GroupingClause¶

    Member Type Presence Notes
    components Array of String REQUIRED MUST be non-empty.

    Each component MUST be either:

    • an axis token — "r", "c" or "s", denoting the row, column or sheet axis of the operand; or
    • a Component code available on the operand.

    The two namespaces are distinct but share one array. Consumers MUST test for the three axis tokens first and treat any other value as a Component code. Because the tokens are single lower-case letters and Component codes are not, the two cannot collide; Producers MUST NOT emit a Component code equal to "r", "c" or "s".

    Grouping by an axis token partitions on Position Index: group by c produces one group per distinct y. Grouping by a Component code partitions on the reported values of that Component.

    Resolution is after renaming. A Component code MUST be a member name of open_keys for the operand's table (§3.6) as the operand presents it — that is, after applying any RenameClauseOp between the table and the AggregationOp (§4.24). A rule that groups {tC_27.00, c050}[rename INC to GCC] by GCC is well-formed even though GCC is not an Open Key of C_27.00, because the rename put it there. A Consumer that resolves against the unrenamed table will reject such a rule.

    A GroupingClause MUST occur only as the grouping_clause of an AggregationOp.

    Components observed: the axis tokens c (63), r (8), s (12) and the pair r, c (12), and Key Component codes including CEG, SIC, GCC, INC, CUS and their q-prefixed forms.

    { "class_name": "GroupingClause", "components": [ "c" ] }

    4.20 AnalyticClause¶

    The window specification of an analytic AggregationOp (§4.18).

    Member Type Presence Notes
    partition_by Array of String REQUIRED Component codes or axis tokens partitioning the window. MAY be empty, meaning one window over the whole operand.
    order_by Array of Object REQUIRED Sort keys, below. REQUIRED and non-empty when window is present or op is "rank"; otherwise MAY be empty ([]).
    window Object or null REQUIRED, nullable Frame bounds. null means the whole partition. MUST be null when op is "rank".

    Each entry of order_by:

    Member Type Notes
    key_name String Component code, axis token, or the Fact Component f (§4.7).
    direction String "asc" or "desc".

    An AnalyticClause MUST occur only as the analytic_clause of an AggregationOp. When op is "rank", order_by MUST be non-empty and window MUST be null (rank cannot accept a window frame). For general aggregations without a window (e.g. sum({…} over (partition by …))), order_by MAY be empty. Where a window is present, order_by MUST be non-empty.

    A non-null window is an object with the members below. It narrows the window from the whole partition to a frame around each Record, in the manner of an SQL window frame:

    Member Type Presence Notes
    frame_type String REQUIRED "data_points" to count Records, "range" to compare order_by values.
    start Object REQUIRED Lower bound, below.
    end Object REQUIRED Upper bound, below.

    Each bound is an object:

    Member Type Presence Notes
    bound_type String REQUIRED "unbounded_preceding", "n_preceding", "current_data_point", "n_following" or "unbounded_following".
    n Integer OPTIONAL Distance from the current Record. Present only where bound_type is "n_preceding" or "n_following"; absent for the other three, which carry unboundedness or the current position in bound_type itself.

    start MUST not be later than end in window order — unbounded_preceding < n_preceding < current_data_point < n_following < unbounded_following: a start of "unbounded_following" with an end of "unbounded_preceding" describes an empty frame and MUST NOT be emitted. Where frame_type is "range", n is a distance in the Data Type of the sole order_by key, so a "range" frame with an n_preceding/n_following bound requires exactly one order_by entry.

    An unpartitioned window ordered by the fact value descending, with a null frame, is what rank({…} over (order by f desc)) produces:

    { "class_name": "AnalyticClause",
  "partition_by": [],
  "order_by": [ { "key_name": "f", "direction": "desc" } ],
  "window": null }

    A null window is the common case, and a Consumer MUST NOT treat the frame as optional on that account: where one is present it MUST be evaluated as specified rather than ignored, since ignoring it widens the window and changes every rank it produces.

    rank(…) over (…) has no DPM-ML OperatorID (§4.1.2).

    4.21 WhereClauseOp¶

    Restricts a selection by a condition on its Components.

    Member Type Presence Notes
    operand Node REQUIRED The selection to restrict.
    condition Node REQUIRED A BinOp, a UnaryOp or a Dimension Node.

    The condition compares Components to values: its left is normally a Dimension Node (§4.7) and its right a Scalar (§4.5), a Set (§4.6) or a SubstrOp (§4.15), combined with =, != or in, and composed with and/or. It MAY also be a UnaryOp — not(isnull(f)) is the common form — or, where the Fact Component is Boolean, the bare Dimension f. All three shapes occur: 399 BinOp, 11 UnaryOp, 6 Dimension.

    WhereClauseOp narrows which Records the operand contributes but does not renumber them: idx(WhereClauseOp) = idx(operand). See Operators §11 Clause Operators.

    { "class_name": "WhereClauseOp",
  "operand":   { "class_name": "VarID", "table": "C_09.04", "row": "0070", "column": "0010", … },
  "condition": { "class_name": "BinOp", "op": "=",
                 "left":  { "class_name": "Dimension", "dimension_code": "RIO" },
                 "right": { "class_name": "Scalar", "item": "eba_GA:qx2014", "scalar_type": "Item" } } }

    4.22 SubClauseOp¶

    Selects a sub-Record of the operand by fixing a Component the rendering leaves open. Encodes DPM-ML Operator 38, sub.

    Member Type Presence Notes
    operand Node REQUIRED The selection to narrow.
    condition Node REQUIRED Any Node. In practice always a BinOp op: "=" equating a Component to a value, which is the form Operators §11 defines.

    sub differs from where in what it does to the Recordset, not in what it tests: where filters Records and leaves the Component in place, while sub fixes the Component to the given value and drops it, so the result is the single Record at that value. idx(SubClauseOp) = idx(operand). See Operators §11 Clause Operators.

    { "class_name": "SubClauseOp",
  "operand":   { "class_name": "VarID", "table": "C_07.00.a", "row": "0010", "column": "0200", … },
  "condition": { "class_name": "BinOp", "op": "=",
                 "left":  { "class_name": "Dimension", "dimension_code": "qEBB" },
                 "right": { "class_name": "Scalar", "item": "eba_qEC:qx19", "scalar_type": "Item" } } }

    4.23 GetClauseOp¶

    Moves a Component of the operand into the Fact position. Encodes DPM-ML Operator 29, get. The result is a Recordset with the same structure as the operand, so idx(GetClauseOp) = idx(operand); it is not a set. Where a set is wanted, a SetOp supplies it, explicitly or implicitly (§4.14).

    Member Type Presence Notes
    operand Node REQUIRED The selection to project. Any Node yielding a Recordset that carries the named Component.
    component String REQUIRED Component code to project. A plain String, not a Dimension Node.

    component is a bare String even though Dimension (§4.7) exists for the same purpose elsewhere. This is normative; a Consumer MUST NOT expect a Node here.

    The code is resolved as in §4.7.2: a member name of open_keys for the operand's table (§3.6) after any rename, or one of the three reserved contextual codes. Which Components get may be applied to is a semantic question, settled in Operators §11.3.5 — the Fact Component and the standard Key Components r, c and s are excluded there — and this part adds nothing to it.

    refPeriod is the commonest thing a GetClauseOp projects: the reference period of the instance under validation, moved into the Fact as a Date, where it feeds month and year (§4.11).

    See Operators §11 Clause Operators.

    { "class_name": "GetClauseOp",
  "operand": { "class_name": "VarID", "table": "C_29.00", "column": "030", … },
  "component": "INC" }

    4.24 RenameClauseOp¶

    Renames Components of the operand. Encodes DPM-ML Operator 33, rename. idx(RenameClauseOp) = idx(operand). Operator 34 (node) has no encoding in this version and no defined semantics anywhere in this specification; see §5.4.

    Member Type Presence Notes
    operand Node REQUIRED The Recordset whose Components are renamed.
    clauses Array of Object REQUIRED Rename pairs, below. MUST be non-empty.

    Each entry of clauses:

    Member Type Notes
    from_component String Existing Component code on the operand.
    to_component String New code.

    The renames of one Node apply simultaneously, not in sequence: a Consumer MUST compute the new Component set in one step, so that [rename qEGS to qCIN, qLGS to qLIN] — the most common form, 30 occurrences — cannot be affected by the order of its entries. Producers MUST NOT emit a clauses array whose from_component and to_component sets overlap.

    Renaming is what makes an aggregation across two tables alignable, by giving the same Component the same code on both sides. It has consequences for resolution elsewhere: a Component code in a GroupingClause (§4.19), a GetClauseOp (§4.23) or a Dimension (§4.7) resolves against the Component set as renamed, not against the open_keys of the underlying table.

    { "class_name": "RenameClauseOp",
  "operand": { "class_name": "AggregationOp", "op": "sum", … },
  "clauses": [ { "from_component": "GCC", "to_component": "INC" } ] }

    4.25 FilterOp¶

    Restricts a selection by a condition on reported data rather than on Components.

    Member Type Presence Notes
    selection Node REQUIRED The selection to filter.
    condition Node REQUIRED A BinOp or UnaryOp Node yielding Boolean.

    The condition may reference VarID Nodes, which are themselves resolved and MUST be co-located with selection — that is, they select from the same table and the same non-varying axes — so that the condition is evaluable per Record. As with WhereClauseOp, indices are preserved. See Operators §8 Conditional Operators.

    FilterOp differs from WhereClauseOp in the subject of the test: where tests metadata, filter tests values.

    { "class_name": "FilterOp",
  "selection": { "class_name": "VarID", "table": "C_08.02", "column": "0020", "sheet": "0003", … },
  "condition": { "class_name": "BinOp", "op": "=",
                 "left":  { "class_name": "VarID", "table": "C_08.02", "column": "0010", "sheet": "0003", … },
                 "right": { "class_name": "Constant", "type_": "Integer", "value": 1 } } }

    4.26 CondExpr¶

    The if-then-else Operator.

    Member Type Presence Notes
    condition Node REQUIRED MUST yield Boolean.
    then_expr Node REQUIRED Evaluated where condition is true.
    else_expr Node OPTIONAL Evaluated where condition is false. Omitted, not null, where the Operator has no else branch.

    else_expr is OPTIONAL and its absence is significant (§4.1.3). A Producer MUST omit it rather than emit null; a Consumer MUST treat absence, not null, as the one-armed form. The one-armed conditional is the commoner shape of the two, so this is not an edge case a Consumer can defer.

    Where else_expr is absent and condition is false, the Operation yields no result for that Position Index. A Consumer MUST report such an index as not applicable, distinctly from passed and failed. This is the encoding of a one-armed conditional validation — "if these cells are reported, that cell must be reported too" — where the absence of the trigger is not itself a finding.

    Null treatment of condition follows Information Model §4 Null handling: a null condition selects neither branch.

    { "class_name": "CondExpr",
  "condition": { "class_name": "BinOp", "op": ">", … },
  "then_expr": { "class_name": "BinOp", "op": ">", … } }

    4.27 TimeShiftOp¶

    Selects the operand from a different reference period.

    Member Type Presence Notes
    operand Node REQUIRED The selection to shift.
    period_indicator Node REQUIRED MUST be a Constant with type_: "String".
    shift_number Node REQUIRED A Constant with type_: "Integer", or a UnaryOp op: "-" over one.
    reference_period String REQUIRED "refPeriod".

    period_indicator gives the period unit and shift_number the number of units to shift. "A" with 1 denotes one year earlier, "M" with 12 the same span expressed in months. Permitted period indicators are those defined in Operators §10 Time Operators; A, Q and M occur.

    A shift may be forward. shift_number is not restricted to a positive Constant: three occurrences encode -1 as a UnaryOp op: "-" wrapping Constant 1, giving a shift of one quarter later. A Consumer MUST evaluate shift_number as a Node and honour its sign, and MUST NOT read the Constant beneath a negation as if it were the value.

    reference_period names the temporal anchor of the shift. "refPeriod" — the reference period of the instance under validation — is the only value currently assigned; §5.5 reserves the member for further anchors.

    An Operation containing a TimeShiftOp requires an instance for the shifted period and MUST therefore appear in a cross_instance_dependencies entry whose modules include an entry with the corresponding ref_period (§3.11), which for a forward shift is of the form T+<n><p>.

    { "class_name": "TimeShiftOp",
  "operand": { "class_name": "VarID", "table": "F_25.01.a", "row": "0120", … },
  "period_indicator": { "class_name": "Constant", "type_": "String", "value": "M" },
  "shift_number":     { "class_name": "Constant", "type_": "Integer", "value": 12 },
  "reference_period": "refPeriod" }

    A shift of one quarter forward:

    { "class_name": "TimeShiftOp",
  "operand": { "class_name": "VarID", … },
  "period_indicator": { "class_name": "Constant", "type_": "String", "value": "Q" },
  "shift_number":     { "class_name": "UnaryOp", "op": "-",
                        "operand": { "class_name": "Constant", "type_": "Integer", "value": 1 } },
  "reference_period": "refPeriod" }
